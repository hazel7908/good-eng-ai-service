# 환경영향평가 보고서 자동화 — PoC 실행 계획

> 목표: 대기질 파트 1개에 대해 AI 자동화 가능 여부를 빠르게 판단하고, 클라이언트에 피드백 제공

## Phase 0: 자료 수령 및 분석 (목요일 오전)

자료가 도착하면 코드를 쓰기 전에, 사람 눈으로 먼저 파악해야 할 것들이 있다.

### 0-1. 파일 인벤토리

받을 자료 (회의에서 합의된 구성):
- 태양광 대기질 보고서 본문 × 3~4세트 (한글 파일)
- 각 세트별 사업 개요
- 각 세트별 측정 성적서
- 각 세트별 도면

**확인 사항:**
- [ ] 실제로 몇 세트가 왔는지
- [ ] 파일 포맷 확인 (HWP인지 HWPX인지, PDF인지)
- [ ] 파일 크기 및 쪽수 확인
- [ ] 누락된 구성요소가 있는지

### 0-2. 레퍼런스 간 비교 분석 (핵심)

3~4개 세트의 대기질 본문을 나란히 놓고 비교한다. 이 단계가 PoC 전체의 방향을 결정한다.

**분석 항목:**

(a) 문서 구조 매핑
- [ ] 각 보고서의 목차/섹션 구조를 추출하여 나란히 비교
- [ ] 섹션 순서가 동일한지, 섹션 수가 같은지
- [ ] 표의 개수, 위치, 구조가 일관되는지

(b) 고정 vs. 가변 영역 식별
- [ ] 3~4개 보고서에서 완전히 동일한 문장/단락 표시 (고정 영역)
- [ ] 지역명·수치만 다른 문장/단락 표시 (단순 치환 영역)
- [ ] 서술 내용 자체가 다른 문장/단락 표시 (생성 필요 영역)
- [ ] 각 영역의 대략적인 비율 파악 (예: 고정 40%, 치환 35%, 생성 25%)

(c) 변수 목록 정리
- [ ] 케이스마다 바뀌는 변수를 모두 추출하여 리스트화
- [ ] 각 변수의 출처 확인 (개요에서 오는지, 측정서에서 오는지, 외부 데이터인지)
- [ ] 동일 변수가 문서 내 몇 군데에 반복 등장하는지 카운트

(d) 토큰 수 측정
- [ ] 대기질 본문 1개의 텍스트를 추출하여 토큰 수 측정
- [ ] 개요 + 측정서의 텍스트 토큰 수 측정
- [ ] 레퍼런스 3개 + 인풋 자료를 모두 넣었을 때 총 토큰 수 산출
- [ ] Opus 4.5/4.6의 100만 토큰 컨텍스트 내에 들어오는지 확인

### 0-3. 인풋 자료 구조 파악

- [ ] 사업 개요 파일: 어떤 정보가 어떤 형식으로 담겨 있는지
- [ ] 측정 성적서: 수치 데이터가 어떤 형태인지 (표? 텍스트? 이미지?)
- [ ] 도면: 이번 PoC에서는 제외하되, 어떤 정보가 추출 가능한지 확인만

## Phase 1: 텍스트 추출 및 전처리 (목요일 오후)

한글 파일에서 텍스트를 추출하여 AI가 처리할 수 있는 형태로 만든다.

### 1-1. HWP/HWPX 텍스트 추출

**방법 A (HWPX인 경우):**
- ZIP 해제 → Contents/section0.xml 파싱
- BeautifulSoup 또는 xml.etree로 텍스트, 표 추출
- OS 독립적, 추가 소프트웨어 불필요

**방법 B (HWP인 경우):**
- libhwp (Python, 크로스플랫폼): 문단·표 텍스트 읽기 가능
- pyhwpx (Windows + 한글 설치 필요): 더 풍부한 API
- 최악의 경우: 한글에서 텍스트 복사 → 수동으로 텍스트 파일 생성

**산출물:**
- 레퍼런스 보고서 3~4개의 대기질 본문 텍스트 (마크다운 또는 플레인텍스트)
- 개요 텍스트
- 측정 성적서 수치 데이터 (구조화된 형태)

### 1-2. 폴더 구조 설계

Cowork/Claude Code가 탐색할 작업 폴더 구조를 설계한다.

```
poc_workspace/
├── instructions.md              ← 에이전트 지침 (Phase 2에서 작성)
├── references/                  ← 레퍼런스 보고서들
│   ├── ref_01_여주_광대리/
│   │   ├── 대기질_본문.txt
│   │   ├── 사업개요.txt
│   │   └── 측정성적서.txt
│   ├── ref_02_충주_OO/
│   │   ├── 대기질_본문.txt
│   │   ├── 사업개요.txt
│   │   └── 측정성적서.txt
│   └── ref_03_홍천_OO/
│       ├── ...
├── input/                       ← 이번 케이스의 인풋
│   ├── 사업개요.txt
│   └── 측정성적서.txt
└── output/                      ← AI가 생성한 초안
    └── (여기에 결과물이 생성됨)
```

## Phase 2: 프롬프트/Instructions 설계 (목요일 저녁 ~ 금요일 오전)

Phase 0의 분석 결과를 바탕으로, AI에게 줄 지침을 설계한다. 이 단계가 PoC의 품질을 결정하는 핵심 작업.

### 2-1. 시스템 Instructions 설계

Cowork의 폴더 instructions 또는 Claude Code의 CLAUDE.md에 해당하는 문서.

포함해야 할 내용:
- 역할 정의: "환경영향평가 보고서의 대기질 파트를 작성하는 초급 실무자"
- 작업 절차: 레퍼런스를 어떤 순서로 참조하고, 어떤 단계로 작성할지
- 품질 기준: 어떤 수준의 정확도를 목표로 하는지 (틀려도 되는 부분 명시)
- 변수 처리 규칙: 인풋에서 변수를 추출하여 문서 전체에 일관되게 적용하는 방법
- 문체 가이드: 레퍼런스의 문체를 따르되, 어떤 톤과 표현을 사용할지

### 2-2. 작업 프롬프트 설계

실제로 AI에게 줄 작업 지시. Phase 0의 분석 결과에 따라 크게 두 가지 전략 중 택일:

**전략 A: 섹션 순차 생성 (구조가 매우 정형적인 경우)**
1. "references/ 폴더의 보고서들에서 대기질 본문의 구조를 분석해줘"
2. "input/ 폴더의 개요와 측정서를 읽어줘"
3. "섹션 1(현황 및 조사개요)을 작성해줘. 레퍼런스의 해당 섹션을 참고하되, 이번 케이스의 인풋으로 치환해서"
4. "섹션 2(측정 결과)를 작성해줘..."
5. (반복)
6. "전체를 output/ 폴더에 저장해줘"

**전략 B: 일괄 생성 (토큰 수가 여유 있는 경우)**
1. "references/ 폴더의 모든 레퍼런스와 input/ 폴더의 인풋을 읽고, 대기질 보고서 초안 전체를 작성해줘"

→ Phase 0의 토큰 측정 결과에 따라 결정. 대부분의 경우 전략 A가 현실적일 것으로 예상.

## Phase 3: 생성 테스트 및 반복 (금요일)

### 3-1. 첫 번째 생성 (베이스라인)

**테스트 설계:**
- 레퍼런스 3개 중 1개를 "정답지"로 빼놓는다
- 나머지 2개를 레퍼런스로 제공하고, 빼놓은 1개의 인풋(개요+측정서)을 줌
- AI가 생성한 초안을 "정답지"와 비교

이 방식이면 "AI가 생성한 것 vs. 실제 사람이 작성한 것"을 직접 비교하여 품질을 객관적으로 판단할 수 있다.

**비교 항목:**
- [ ] 문서 구조 일치도: 섹션 순서, 표 구조가 정답지와 얼마나 유사한가
- [ ] 고정 내용 재현율: 법령 인용, 표준 문구 등이 정확히 들어갔는가
- [ ] 변수 치환 정확도: 지역명, 수치 등이 올바르게 치환되었는가
- [ ] 서술 품질: 자연스러운 한국어인가, 보고서 문체에 맞는가
- [ ] 환각(hallucination) 발생: 인풋에 없는 정보를 지어낸 부분이 있는가
- [ ] 누락: 정답지에 있는데 AI 초안에 빠진 내용이 있는가

### 3-2. 반복 개선 (2~3회)

첫 번째 결과를 보고 instructions/프롬프트를 수정하여 재시도.

**예상되는 개선 포인트:**
- 특정 섹션에서 구조가 틀어지면 → 해당 섹션의 지침을 더 구체화
- 변수 치환이 누락되면 → 변수 체크리스트를 instructions에 명시
- 문체가 안 맞으면 → 레퍼런스에서 문체 예시를 직접 인용하여 가이드
- 불필요한 내용이 생성되면 → "이 섹션에서는 OO만 다룬다" 등 범위 제한

### 3-3. HWP 출력 테스트 (선택적)

시간 여유가 있으면, 생성된 텍스트를 실제 HWP 파일에 삽입하는 것까지 테스트.

- HWPX 경로: python-hwpx로 템플릿 기반 삽입 시도
- Word 경로: python-docx로 서식 포함 문서 생성
- 이 단계는 PoC 성공 여부 판단에는 불필요 (텍스트 품질이 핵심)

## Phase 4: 결과 정리 및 판단 (금요일 저녁 ~ 주말)

### 4-1. PoC 결과 판단 기준

**GO 판단 (진행 가능):**
- AI 초안이 "정답지"와 구조적으로 80% 이상 일치
- 차장급이 이 초안을 받아서 3~4일 내 디벨롭 가능한 수준
- 치명적 환각(완전히 틀린 수치, 존재하지 않는 법령 인용 등)이 없거나 극소수

**CONDITIONAL GO (조건부 진행):**
- 일부 섹션은 잘 되지만 특정 섹션에서 품질이 떨어짐
- → 잘 되는 섹션만 자동화하고, 나머지는 수동으로 남기는 부분 자동화 제안

**NO-GO (중단 또는 재설계):**
- 구조 자체를 잡지 못하거나, 환각이 빈번하거나, 변수 치환 오류가 과다
- → 클라이언트에게 솔직히 현 단계 한계를 전달하고, 대안 제시

### 4-2. 클라이언트 전달 자료 구성

PoC 결과에 따라 아래 문서를 작성하여 전달:

1. **PoC 결과 보고서**: 테스트 방법, 비교 결과, 품질 평가
2. **납품 방식 제안서**: Cowork 기반 vs. 커스텀 에이전트, 각각의 비용·보안·일정
3. **단계별 로드맵**: Phase별 확장 계획과 예상 일정
4. **견적**: (PoC 결과에 따라 범위 확정 후)
