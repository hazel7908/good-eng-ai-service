# 프로젝트 로드맵 — 현실적 평가와 다음 단계

> 작성일: 2026-03-06
> 목적: PoC 결과를 기반으로, 이 프로젝트가 실무에 투입 가능한지 평가하고 협업 방식을 정리

## 1. 현재까지 증명된 것

### PoC 결과 요약 (소음·진동 파트)

| 항목 | 수치 |
|------|------|
| 전체 비교 항목 | 61건 |
| 정확 (OK) | 27건 (44%) |
| 오류 (WRONG) | 19건 (31%) |
| 누락 (MISSING) | 7건 (11%) |
| 추출 불가 (UNAVAIL) | 4건 (7%) |
| 불필요 변경 (EXTRA) | 1건 (2%) |
| 표기 차이 (MINOR) | 3건 (5%) |

### 오류 19건의 내역

잘못된 것이 **19건**이지만, 원인을 보면 독립적인 실수는 적다:

| 근본 원인 | 파생 오류 수 | 수정 난이도 |
|----------|:----------:|:---------:|
| 삽도 이격거리 오차 4건 → 예측값 연쇄 | 10건 | 삽도가 아닌 실측값 받으면 해결 |
| 저감량 계산 방식 오류 | 4건 | 공식 1곳 수정 |
| 기준 체계 혼동 | 1건 | 매핑 룰 1줄 수정 |
| 테이블 셀 탐색 오류 | 1건 | 검색어 수정 |
| FindReplace 미매칭 2건 + 서술 미변경 1건 | 3건 | 분기 로직 추가 |

**핵심**: 근본 원인은 5가지뿐. 이것들을 수정하면 WRONG 19건 중 대부분이 해소된다.

### 증명된 기술적 가능성

- 한글 API(win32com)로 HWPX 자동 생성 **가능** (파일 무결성 문제 없음)
- 텍스트 치환 + 표 셀 편집 + 행 추가 + 이미지 교체 **모두 가능**
- 인풋 텍스트(사업개요 + 환경질측정 보고서)에서 필요한 변수 자동 추출 **가능**
- 계산 공식 자동화 **가능** (합성소음도, 이격거리별 예측값 등)

## 2. 대표가 미팅에서 말한 목표와 현실

### 대표의 기대

> "3주 걸리는 작업을 1주일이면 된다"
> - 개요 작성: 1일 (회사가 수동으로)
> - AI 자동 생성: 반나절
> - 선임 디벨롭: 3~4일

### 현재 업무 규모

- 연간 **~200건** 보고서 작성
- 신입 기준 **2주**, 대표 본인도 **10일** 소요
- 보고서 1건 = 약 **10개 파트** (14개 중 선택)
- 파트 1개 = 약 **14~20쪽** (소음진동 기준)

### 자동화 효과 추정

소음·진동 1개 파트 기준:

| 단계 | 현재 (수동) | 자동화 후 |
|------|:---------:|:--------:|
| 레퍼런스 읽기 + 복사 | 2~3시간 | 0분 (스크립트 실행) |
| 변수 치환 (사업명, 주소, 측정값) | 1~2시간 | 0분 (자동) |
| 계산 (합성소음도, 예측값 등) | 1~2시간 | 0분 (자동) |
| PP 데이터 입력 | 30분~1시간 | 0분 (인풋 파일에서 자동 추출) |
| 법령표 확인 | 30분 | 0분 (국가법령정보센터에서 자동 확인 가능) |
| 전체 검수 | 1~2시간 | 1~2시간 (선임 검수는 여전히 필요) |
| **합계** | **6~10시간** (1~1.5일) | **1~2시간** (검수만) |

10개 파트 전체에 적용하면:
- 현재: 신입 기준 **2~3주/건**, 대표도 **10일/건**
- 자동화 후: **개요 작성 1일 + AI 생성 반나절 + 선임 디벨롭 3~4일 = 약 1주/건**

### 실제 인력 효과

현재 7명이 연간 200건을 처리한다면:
- 1인당 약 **30건/년** 담당
- 보고서 1건에 2~3주 → 연중 거의 보고서만 씀

자동화 후:
- 보고서 1건이 **1주**로 줄면 → 1인당 **50건/년** 처리 가능
- 같은 200건을 **4명**으로 처리 가능 → **신입 2~3명을 덜 뽑아도 됨**
- 또는 같은 인원이면 보고서 외 다른 업무에 시간을 쓸 수 있음

## 3. 실현 가능한 운영 모델

### 미팅에서 대표가 언급한 환경

- Windows PC + 한글 프로그램 (필수)
- NAS 스토리지에 레퍼런스 보관
- ChatGPT 유료 계정 사용 중 (판단 보조용)
- 보안 우려: 도구 자체가 퇴사자와 함께 유출되지 않길 원함

### 제안: Git 레포 기반 운영

```
[Git Repository: good-eng-ai-service]
    │
    ├── .claude/rules/          ← 도메인 지식 (기준 체계, 변수 매핑, 공식)
    ├── .claude/skills/         ← 워크플로우 (/generate-report, /validate-report)
    ├── scripts/                ← 생성 스크립트
    ├── templates/              ← HWPX 템플릿
    └── references/             ← 레퍼런스 보고서

[회사 직원 워크플로우]
    1. git pull (최신 지식/스크립트 가져오기)
    2. tests/{섹션}/input/ 에 인풋 파일 배치
    3. Claude Code에서 /generate-report 실행
    4. 생성된 HWPX를 한글에서 열어 선임 검수
```

### 이 모델의 장점

1. **지식이 레포에 축적**: 오류 발견 → rules에 추가 → 다음 생성에서 자동 반영
2. **직원 의존도 낮음**: 도메인 지식이 사람 머릿속이 아니라 파일에 있음
3. **보안**: Private repo로 관리. 퇴사자 계정 제거하면 접근 차단
4. **점진적 확장**: 파트별로 rules 파일 추가하면 됨

### 이 모델의 리스크

| 리스크 | 심각도 | 대응 |
|--------|:-----:|------|
| 직원이 Claude Code 사용법을 모름 | 높음 | 초기 교육 + 매뉴얼. 실제로는 `/generate-report` 치고 인풋 파일 위치만 알면 됨 |
| Claude API 비용 | 중간 | 보고서 1건당 대화 비용 추정 필요. 인건비 절감 대비 미미할 가능성 높음 |
| 한글 API 환경 세팅 | 중간 | Python + pywin32 설치가 필요. 한번 세팅하면 유지 |
| 인풋 자료 품질 편차 | 중간 | 환경질측정 보고서 포맷이 측정업체마다 다를 수 있음 → 추출 규칙 보강 필요 |
| 법령 개정 | 낮음 | 국가법령정보센터에서 자동 확인 가능. 개정 감지 시 알림 |

### 도구 종속성 — "Claude가 아니면 못 쓰나?"

**결론: 아니다.** 이 레포는 특정 AI 도구에 종속되지 않는 구조.

#### 레포 안의 파일별 종속성

| 파일/디렉토리 | Claude 전용? | 설명 |
|---|:---:|---|
| `scripts/*.py` | ❌ | 순수 Python + win32com. AI 도구와 무관 |
| `templates/` | ❌ | HWPX 파일. 도구 무관 |
| `tests/` | ❌ | 인풋/정답 데이터. 도구 무관 |
| `.claude/rules/*.md` 내용 | ❌ | 마크다운으로 작성된 도메인 지식 (공식, 변수 매핑, 분기 로직). 어떤 AI든 읽을 수 있음 |
| `.claude/skills/*.md` 내용 | ❌ | 워크플로우 절차서. 어떤 AI든 따를 수 있는 단계별 지침 |
| `CLAUDE.md` | ⚠️ | 파일명이 Claude Code 컨벤션. 내용 자체는 범용적인 프로젝트 개요 |
| `.claude/` 디렉토리 경로 | ⚠️ | Claude Code의 규칙 로딩 경로. 다른 도구에선 경로만 변경하면 됨 |

#### 만약 다른 AI 도구로 전환한다면

변경이 필요한 것:
- `CLAUDE.md` → 해당 도구의 설정 파일명으로 변경 (예: `.cursorrules`)
- `.claude/` → 해당 도구의 규칙 디렉토리로 이동 또는 참조 경로 변경

변경이 **불필요**한 것:
- Python 스크립트 전체
- 도메인 지식 (공식, 변수 매핑, 오류 패턴) — 마크다운이라 그대로 사용
- 템플릿, 테스트 데이터, 문서

**핵심**: SaaS처럼 데이터가 플랫폼 안에 갇히는 구조가 아님. 모든 지식이 Git 레포 안에 마크다운 + Python으로 존재하고, AI 도구는 이 파일들을 읽고 실행해주는 "런타임"일 뿐이다. 퇴사자가 레포 접근 권한을 잃으면 도구도, 지식도 함께 차단된다.

## 4. 프로젝트 단계별 계획

> 풀타임이 아닌 병행 개발 기준. 프로젝트 시작일 기준 상대 일정.
> 개발 과정에서는 정답지 비교로 자체 검증. 실무자 피드백은 실제 사용 단계에서 자연스럽게 수집.

```
1개월차          2~5개월차                                    6개월차
├─ Phase 1 ──────┤
│ 소음진동 완성   ├──────── Phase 2 ──────────────────────────┤
│ (PoC 기반)      │ 나머지 9개 파트 순차 확장 (파트당 1~2주)   ├─ Phase 3
│                 │                                           │ 안정화
│                 │                                           │
├─ 실무 투입 ─────┴───────────────────────────────────────────┘
│ (파트 완성될 때마다 바로 사용 가능)
```

### Phase 1: 소음·진동 완성 (1개월차)

**목표**: PoC에서 발견된 오류 수정 → 소음·진동 파트 실무 투입

| 작업 | 내용 | 클라이언트 필요 사항 |
|------|------|------|
| 오류 수정 5건 | 기준 혼동, 저감량 계산, 테이블 매칭, 서술 분기, 발생원 현황 | - |
| 새 사업 테스트 | 괴산 외 다른 태양광 사업으로 생성 → 정답지 비교 검증 | ⚠️ 다른 태양광 인풋 자료 1~2세트 + 정답 보고서 |
| 인풋 포맷 검증 | 다른 측정업체 보고서도 파싱 가능한지 확인 | ⚠️ 다른 측정업체 성적서 샘플 |

**이 시점에서**: 소음·진동 파트 실무 투입 가능

### Phase 2: 나머지 9개 파트 확장 (2~5개월차)

**목표**: Phase 1과 동일한 프로세스로 나머지 파트 순차 적용

파트마다 동일한 사이클 반복:
1. 레퍼런스 3~4개에서 변수 매핑 추출
2. `.claude/rules/{파트}.md` 작성
3. 생성 스크립트 작성 (Phase 1 구조 재활용)
4. 정답지 대비 비교 검증, 오류 수정
5. 완성 → 바로 실무 투입

| 순서 | 파트 | 난이도 | 이유 |
|:---:|------|:---:|------|
| 1~3 | 대기질, 수질, 토지이용 | 낮음 | 구조 단순, 변수 적음 |
| 4~6 | 악취, 위락시설, 전파장해 등 | 중간 | 표 구조 유사, 분기 로직 약간 |
| 7~9 | 동식물, 경관, 문화재 등 | 중~높음 | 서술형 비중 높아 변수화 어려울 수 있음 |

> 쉬운 파트는 1주, 어려운 파트는 2주. 순서는 클라이언트와 협의.

**클라이언트**: 파트별 레퍼런스 3~4세트 + 인풋 + 정답 보고서를 순차 제공

### Phase 3: 실무 운영 안정화 (6개월차)

**목표**: 개발자 없이 회사가 자체 운영 가능한 상태

| 작업 | 내용 |
|------|------|
| 실무자 교육 | Claude Code 사용법, `/generate-report` 워크플로우, git pull 루틴 |
| 매뉴얼 작성 | 인풋 파일 준비 → 생성 → 검수까지 단계별 가이드 |
| 프로세스 표준화 | 인풋 파일 네이밍, 폴더 구조, 검수 체크리스트 |
| 이관 | 담당 직원 1명 지정, 독립 운영 확인 후 유지보수 전환 |

## 5. 협업 구조 제안

### 나(개발자)의 역할

| 단계 | 역할 | 형태 |
|------|------|------|
| Phase 1~2 | 직접 개발 | rules 작성, 스크립트 개발, 오류 수정 |
| Phase 3 | 이관 + 기술 지원 | 교육, 매뉴얼, 신규 오류 대응 |
| 이후 | 유지보수 | 월 n시간 기술 지원 계약 |

### 회사(클라이언트)의 역할

| 단계 | 역할 |
|------|------|
| Phase 1~2 | 파트별 레퍼런스 + 인풋 + 정답 보고서 순차 제공 |
| Phase 2~ | 완성된 파트부터 실무 사용, 사용 중 오류 리포트 |
| Phase 3~ | 직원 1명 담당자 지정 (git pull + Claude Code 실행), 자체 운영 |

### NAS 접근 vs 자료 전달

| 방식 | 장점 | 단점 |
|------|------|------|
| **NAS 접근권한 받기** | 레퍼런스 직접 탐색 가능. 효율적 | 보안 우려. 대표가 원하지 않을 수 있음 |
| **자료 전달 방식** | 보안 우려 없음 | 매번 요청 필요. 느림 |
| **하이브리드** | Phase 1~2는 자료 전달, Phase 3부터 NAS 접근 | 신뢰 구축 후 접근 확대 |

대표의 보안 우려("퇴사자가 들고 나가지 않았으면")를 고려하면, **하이브리드** 방식이 현실적.

## 6. 이 프로젝트가 의미 있는가?

### 숫자로 보면

| 항목 | 값 |
|------|:--:|
| 연간 보고서 | ~200건 |
| 현재 소요 (신입 기준) | 2~3주/건 |
| 자동화 후 예상 | 1주/건 |
| 같은 200건 처리에 필요한 인원 | 7명 → 4명 |
| **신입 채용 절감** | **2~3명분** |

### 기술적으로 보면

- 한글 API 기반 자동화는 **실증됨** (PoC 완료)
- 보고서 구조가 **고정 포맷** → 자동화에 매우 적합
- 오류 허용도가 높음 ("틀려도 괜찮아요. 디벨롭할 때 선임이 잡아냅니다")
- 인풋이 명확 (개요 + 측정 성적서 + 도면)

### 미팅에서 대표가 이미 검증한 것

> "이 프로그램에 넣어서 에디팅해서 반나절이 나오면, 3주 정도 걸리는 작업이 1주일이면 된다"

대표가 **이미 ROI를 계산하고** 이 프로젝트를 시작했다. 문제는 "가능한가"였고, PoC가 "가능하다"를 보여줬다.

### 남은 리스크

1. **인풋 포맷 편차**: 측정업체마다 환경질측정 보고서 포맷이 다를 수 있음 → 추출 규칙 범용화 필요
2. **파트 간 난이도 차이**: 소음진동은 계산이 단순한 편. 대기질/수질은 더 복잡할 수 있음
3. **직원 수용도**: Claude Code 사용법을 직원이 배울 의지가 있는지
4. **대표가 미팅에서 언급한 "10%만 기계적"**: 나머지 90%가 정말 자동화 불가한 건지, 아니면 PoC를 더 해봐야 아는 건지

### 결론

**의미 있다.** 다만 "AI가 완벽한 보고서를 만든다"가 아니라, **"신입이 2주 걸리는 초안 작업을 반나절로 줄인다"**가 현실적인 가치 제안.

대표가 말한 그대로: 초안 → 선임 디벨롭. AI가 선임을 대체하는 게 아니라 **신입의 반복 작업을 대체**하는 것. 이 포지셔닝이 맞으면, 44%의 정확도도 시작점으로 충분하다. 어차피 선임이 검수한다.
