# 레포 구조 설계 — 전 영역 서비스 기준 백지 설계 + PoC 아카이브

> **작성일**: 2026-07-27 · **개정**: 2026-07-28 (3.5단계 검증 결과 반영 — 열린 결정 ① 확정) · **상태**: 초안
> **전제 문서**: 설계 원칙은 [`knowledge_architecture.md`](./knowledge_architecture.md) §1~10 참조
> **한 줄 요약**: PoC 산출물을 옮겨 담는 게 아니라, **전 영역 서비스 기준으로 구조를 백지에서 설계**하고 → PoC는 통째로 아카이브 → 새 구조의 빈자리를 **아카이브에서 복사해 채운다**.

---

## 0. 접근 방식 — 왜 "이동"이 아니라 "백지 설계 + 끌어올리기"인가

이 문서의 초판은 **이동 매핑표**였다: "`tests/소음진동/` → `cases/괴산_금신리/`" 식으로 기존 파일마다 갈 곳을 정해주는 방식. **폐기했다.**

**이유**: 옮길 곳을 찾아주는 순간 그건 이미 승계된 것이다. PoC의 축(파트 1개, 사업 1개, 테스트 중심)이 새 구조에 그대로 딸려온다. 실제로 이동 방식으로 짠 초판은 아래 **§2 ①~③을 전부 놓쳤다** — 서비스에서 출발하니 바로 보였다. (④는 설계가 아니라 방침 결정이라 별개.)

**대체 절차**:

```
1. 전 영역 서비스 기준으로 새 구조를 백지에서 설계   ← 기존 파일 목록을 보지 않고
2. PoC 일체를 _archive/poc-2026-03/ 에 통째로 이동    (원본 그대로, 손대지 않음)
3. 새 구조의 각 자리를 보며 "여기 채울 게 아카이브에 있나?" → 복사해 채움
```

핵심은 **기본값이 아카이브**라는 것이다. 남기려면 적극적 판단이 필요해지고, 그게 관성 승계를 막는다. 복사이므로 아카이브 원본은 그대로 남아 실수해도 복구 가능하다.

## 1. 전제 — 경로 스코핑 (동작 확인됨)

`knowledge_architecture.md` §6(경로 스코핑 = 규모 해법)이 실제 동작하는 기능인지 확인했다. **동작한다.**

### ⚠️ 먼저 — 흔한 오해

> ❌ "항상 로드되는 `CLAUDE.md`·`common.md`가 *'소음진동 작업이면 소음진동.md를 참조하라'* 고 **안내**해서, Claude가 그 안내를 따라 읽는다"

**아니다.** 어떤 문서도 트리거하지 않는다. **하니스(Claude Code 프로그램)가 기계적으로 주입**한다:

```
Claude가 파일을 연다  →  하니스가 그 경로를 각 rule의 paths 와 대조
                      →  매칭되면 그 rule 본문을 컨텍스트에 밀어 넣는다
```

Claude의 판단·기억이 개입하지 않는다. **파일을 여는 행위 자체가 트리거**다.

> 이 차이가 결정적이다. "문서가 안내" 방식이면 Claude가 그 안내를 **읽고·기억하고·따라야** 하므로 보장이 없다. 지금 방식은 Claude가 잊어도 하니스가 강제로 넣는다.
> → 그래서 **경로(폴더 구조)가 곧 지식 스코핑 설계**다. 이 문서가 중요한 이유.

### 동작 모델

```
세션 시작:  .claude/rules/*.md 스캔
            ├─ paths 없음 → 즉시 컨텍스트에 로드
            └─ paths 있음 → 대기 목록 등록
파일 열 때: 연 파일의 경로 ↔ 대기 목록의 경로 패턴 대조
            ├─ 매칭 + 컨텍스트에 없음 → 주입
            └─ 매칭 + 이미 있음      → 재주입 안 함 (중복 제거)
```

**용어**: "컨텍스트에 로드" = 그 파일 내용이 **Claude가 실제로 보고 있는 텍스트에 붙여넣어진다**는 뜻. 로드되지 않은 파일은 디스크에 있어도 Claude에게는 **존재하지 않는다.**

#### 이 분기를 정확히 읽는 법 (혼동 주의)

분기 기준은 **rule 파일 자신이 `paths:` 프론트매터를 갖고 있느냐**다. 사용자 요청 내용과 무관하며, 세션 시작 시점(사용자가 말 걸기 전)에 이미 갈린다.

| rule 파일 | `paths:` | 선언하는 것 | 로드 시점 |
|---|:---:|---|---|
| `.claude/rules/common.md` | **없음** | "나는 무슨 작업이든 필요하다" | 세션 시작 시 **즉시** |
| `.claude/rules/hwpx.md` | `scripts/**` `templates/**` | "저 폴더를 건드릴 때만 불러라" | 그 폴더 파일을 열 때 |
| `.claude/rules/소음진동.md` | `tests/소음진동/**` … | 〃 | 〃 |

> ❌ **오해 A**: "rules 폴더냐 아니냐로 갈린다" → **셋 다 `.claude/rules/` 안의 rule 파일이다.** 차이는 파일 맨 위 몇 줄뿐.
> ❌ **오해 B**: "`scripts/**` 는 파일의 분류(종류)다" → **아니다. `scripts/` 는 레포 루트의 코드 폴더**이고, `paths:` 는 rule이 **가리키는 조건**이다. hwpx.md 자신이 스크립트라는 뜻이 아니라, "코드 만질 때 필요하니 그때 불러달라"는 선언이다.

```
.claude/rules/hwpx.md  ──"나를 언제 부를까?"──→  paths: scripts/**
                                                        │
                                          레포루트/scripts/generate.py 열기
                                                        │
                                                        ▼
                                              hwpx.md 본문 주입
```

#### 왜 paths 있는 걸 그냥 다 미리 로드하지 않나

**그렇게 하면 안 되는 것이 이 설계 전체의 존재 이유다.** 컨텍스트는 유한하고, 분량이 늘면 지시 준수율이 떨어진다 — 이 레포가 이미 겪었다 (`repo_structure_guide.md` §1: "CLAUDE.md 524줄에 전부 담았더니 지시 준수율이 떨어짐").

| | 현재 | 전 영역 확장 후 |
|---|---|---|
| 파트 rule | 1개 (`소음진동.md` 8KB) | 카테고리 ~10 × 파트 ~10 ≈ **100개, 800KB** |
| 전부 로드 시 | 견딤 | **컨텍스트 붕괴** |
| 스코핑 시 | 8KB | **8KB** (파트 1개분) |

분량만의 문제도 아니다. 소음·대기·수질 **기준표가 동시에 떠 있으면 서로 비슷해 혼동을 부른다** — PoC의 Critical 오류 1번이 정확히 기준 분류 혼동('나' ↔ '다')이었다. 지금 안 쓰는 기준표는 **안 보이는 편이 낫다.**

> 즉 **`paths:` 가 있다 = "지금은 로드하지 말라"는 선언**이다. 필요한 순간에 자동으로 들어온다.

#### 요청한 카테고리의 rule이 아직 없으면?

**참고할 파트 지식이 없다 — 그리고 그게 정상이다.** 예: `rules/disaster-impact/` 를 아직 만들지 않았는데 재해영향평가를 요청받으면, 가진 것은 `common.md`(공통 원칙) + `hwpx.md`(기술)뿐이다. 이때 할 일은 **생성이 아니라** 골든셋을 분석해 그 카테고리 rule을 새로 만드는 것이다 (없는 지식으로 생성하면 `common.md` 의 "환각 금지" 위반). → §11 "안 닫는 것"의 카테고리 확장 작업.

### 실무 함의 — 이 검증이 작업에 남기는 것 4가지

| 확인된 것 | 작업에 미치는 영향 |
|---|---|
| **경로 스코핑 동작함** | §5 흐름의 1·4단계(자동 주입)가 성립. 안 됐다면 설계가 아예 달라졌다 (nested CLAUDE.md 등) |
| **중복 제거 있음** | rule 로드를 테스트할 때 **그 rule 파일을 손으로 먼저 읽으면 테스트가 무효**가 된다 (실제로 한 번 오판했다) |
| **세션 중 생성한 rule은 미등록** (추정) | 실행 2·4단계에서 rule을 만든 뒤 **세션 재시작해야** 확인 가능 |
| ~~**하위 디렉터리는 미검증**~~ → **지원 확인됨** (2026-07-28) | 열린 결정 ① 닫힘. 목표 구조 §3 그대로 진행, 평면 네이밍 폴백 폐기 |

> **왜 굳이 검증했나**: `paths:` 가 무시돼도 **에러가 나지 않는다**(조용한 실패). 문서에 "동작한다"고 적혀 있고 아무도 틀렸다고 말해주지 않는다. 파일을 다 옮긴 뒤 알면 롤백 비용이 크고, 사전 확인은 30초다.

## 2. 설계 결정 4가지

이동 방식으로는 안 보였고, 서비스 기준으로 보니 나온 것들.

### ① 폴더·파일 이름 표기 — **경로 패턴에 글자로 박히는 것만 영문** ✅ 확정

축마다 답이 다르다. 하나로 통일하려던 게 오류였다.

**용어 — 경로 패턴(glob)**: 파일을 하나하나 나열하는 대신 *"이런 모양의 경로들"* 로 뭉뚱그려 쓰는 문법. 기호는 사실상 둘뿐이다.

| 기호 | 뜻 | 예 |
|---|---|---|
| `*` | **한 칸**의 아무 이름 (`/` 는 넘지 않음) | `cases/*/input` → `cases/괴산_금신리/input` ✅ / `cases/a/b/input` ❌ |
| `**` | **몇 단계든** 하위 전부 | `scripts/**` → `scripts/` 아래 모든 파일 |

**이름 표기가 여기서 갈린다** — 경로 패턴 하나를 뜯어보면 자리마다 성격이 다르다:

```
cases/small-env/*/noise-vib/**
      └───┬───┘ ┬ └───┬───┘
       카테고리  │    파트
      "글자로   │   "글자로
       박힘"    │    박힘"
               사업
             = * (와일드카드)
```

### 결론

| 축 | 경로 패턴에서 | **표기** | 예 |
|---|---|:--:|---|
| 인프라 폴더 | 글자로 박힘 | **영문** | `templates/` `golden/` `cases/` `engine/` `catalog/` |
| **카테고리** | 글자로 박힘 | **영문** | `small-env` |
| **파트** | 글자로 박힘 | **영문** | `noise-vib` |
| **사업** | `*` 로만 쓰임 | **한글** | `괴산_금신리` |
| 내용 전부 | (경로 아님) | **한글** | rule 본문 · 문서 · 보고서 · 변수명 |

**한 줄로**: 매칭에 실제로 쓰이는 이름만 영문. 사업은 `*` 라 영문화해도 **얻는 게 없는데**, 290건 이상이 계속 늘고 영문 표기가 사람마다 갈리며(`goesan`/`gwesan`) 한글 검색도 막힌다.

> 파트는 한글로 해도 어차피 이름을 다듬어야 한다 — 목차 용어가 `소음·진동`·`동·식물상`이라 가운뎃점 때문에 경로에 그대로 못 쓴다. `소음진동` 도 이미 다듬은 이름이므로 영문으로 간다고 더 멀어지지 않는다.

### ② 사업 작업공간은 `cases/` 하나로 — **전부 커밋**

#### ⚠️ 대전제 — 타임라인이 둘이다 (혼동 주의)

폴더 역할을 이해하려면 **두 단계가 별개**임을 먼저 잡아야 한다. 앞 단계의 산출물이 뒤 단계의 입력이다.

```
【A. 구축 단계 — 지금 우리가 하는 일】
   입력:  golden/ (회사 완성 보고서 5건)
   작업:  분석 → 빈칸 뚫기 · 변수 명세 · 수식 · 분기 규칙 추출
   산출:  templates/  +  .claude/rules/        ★ 우리 작업의 최종 아웃풋
   검증:  괴산 금신리를 생성해 정답과 대조

                    │  A의 산출물이 B의 입력
                    ▼

【B. 운영 단계 — 나중에 실무자가 하는 일】
   입력:  templates/ + rules/  +  신규 사업 input
   산출:  cases/{사업}/…                        보고서 실물
```

> **뒤의 §5(런타임 동작 흐름)는 B만 설명한다.** A는 §9(실행 순서)의 4·6단계다. — 이 문서에는 성격이 다른 '흐름'이 셋 있다: **여기**=폴더가 채워지는 순서 · **§5**=보고서 1건 생성 시 지식이 로드되는 순서 · **§9**=우리가 앞으로 할 작업 순서.
> (`knowledge_architecture.md` §9의 "개발(우리) ↔ 런타임(유저)" 구분과 같은 얘기다.)
> **주의**: `templates/` 는 **아직 없다.** A의 6단계(Windows)에서 원주 무장리 골든셋에 빈칸을 뚫어 만들어야 한다.

#### 폴더가 채워지는 순서

```
golden/    원주·괴산·여주·청양·천안        ← 회사 완성 보고서 5건. 고정. 우리 자산
              │
              │ ① 원주에서 빈칸 뚫어 도출          ┐
              ▼                                  │ A. 구축
templates/ small-env/noise-vib.hwpx  (+ rules/)  │
              │                                  │
              │ ② 괴산 input 으로 채워 생성        │
              ▼                                  ┘
cases/     small-env/괴산_금신리/noise-vib/output.hwpx
              │                                       │
              │                              golden/…/괴산_금신리/원본.hwpx
              │                                       │
              └──────────── 대조 (검증) ───────────────┘
              │
              │ ③ 검증 통과 후 실제 신규 사업에 적용   ┐ B. 운영
              ▼                                     ┘
cases/     small-env/홍성_갈산리/ …           ← 정답 없음. 그냥 납품 작업
```

#### 검증 대상은 폴더가 아니라 `golden/` 짝으로 판별한다

구축 단계의 생성물도, 운영 단계의 납품물도 **똑같이 `cases/{카테고리}/{사업}/`** 에 들어간다. 둘을 가르는 것은 **`golden/` 에 같은 이름의 사업 폴더가 있는가** 뿐이다.

```
cases/small-env/괴산_금신리/   →  golden/small-env/괴산_금신리/ 있음  →  검증 대상
cases/small-env/홍성_갈산리/   →  없음                              →  납품 작업
```

**왜 폴더로 안 나누나** (검토 후 기각):

- 사업명이 이미 폴더를 가르므로 **서로 덮어쓸 위험이 없다.** 재생성은 늘 특정 사업을 지목해 수행한다.
- 오히려 분리하면 손해가 생긴다 — **우리가 만든 보고서가 실제로 납품·완성되면 그게 다음 골든셋이 된다.** 이때 분리 구조에선 폴더를 옮겨야 하지만, 합쳐두면 `golden/` 에 정답을 추가하는 것만으로 자동 편입된다.
- 상태가 `golden/` 한 군데에만 있으므로 어긋날 여지가 없다.

#### git 취급 — 전부 커밋 ✅

| 폴더 | 들어있는 것 | 역할 |
|---|---|---|
| `.claude/rules/` `templates/` | 지식 · 베이스 문서 | **A의 산출물** |
| `golden/` | 레퍼런스 보고서 · 정답 | A의 입력 (고정 자산) |
| `engine/` `catalog/` | 코드 | 도구 |
| `cases/` | 사업별 입력 · 생성물 | 검증 대상 + 납품물 |

**`cases/` 도 커밋하는 이유 (결정)**: 어떤 사업을 · 어떤 입력으로 · 어떤 결과를 냈는지 **이력이 남아야** 한다. 나중에 "이 사업은 왜 이렇게 나왔나"를 추적할 수 있고, 실패 사례가 다음 개선의 재료가 된다. 사내 팀 사용이므로 자료 보안 수준도 NAS에 이미 있는 것과 다르지 않다.

> **지켜볼 것**: HWPX가 누적되면 레포가 무거워진다. 임계에 닿으면 그때 git-lfs 도입이나 오래된 `cases/` 정리를 검토한다. 지금 선제 차단할 문제는 아니다.
> **바뀔 수 있는 조건**: Phase 4에서 웹 서비스가 되면 사용자는 git을 만지지 않으므로 이 결정 자체가 무의미해진다.

### ③ NAS 카탈로그를 독립 하위시스템 `catalog/` 으로

현재 `scripts/build_catalog.py` + `docs/nas_*.json` + `docs/nas_*.md` 로 세 군데 흩어져 있는데, 이건 보고서 생성과 **결합도가 0**이다(입력 데이터 소스를 인덱싱하는 별개 도구). 코드·데이터·산출물을 한 폴더로 묶는다.

### ④ PoC는 통째로 아카이브, 필요한 것만 복사 (§0)

### 왜 이 모양인가 — 폴더 = 개념

`knowledge_architecture.md` §9(용어 정리)의 용어 3개가 **폴더와 1:1로 맞는다.**

| 폴더 | ka §9 용어 | 언제 읽나 | 생성 시 접근 |
|---|---|---|:--:|
| `templates/` | **베이스 문서** | 런타임 생성 **입력** | ✅ |
| `golden/` | **골든셋** | 개발 분석 · 결과 **검증** | ❌ **금지** |
| `cases/` | (사업별 입출력) | 런타임 입력 + 산출물 | ✅ |

`golden/`이 독립 폴더가 되면 `.claude/settings.local.json`의 `permissions.deny`에 `Read(./golden/**)`을 넣어 **"정답지 참조 금지"를 원칙이 아니라 권한으로 강제**하는 길이 열린다(검증 시에만 해제). PoC 구조에선 정답 파일이 `templates/` 안에 있어 애초에 불가능했다.

> ⚠️ **미검증**: 현재 `settings.local.json`에는 `permissions.allow` 만 있다. `deny` + `Read(...)` 문법이 의도대로 동작하는지는 확인하지 않았다 — 구조가 이 강제를 **가능하게 만든다**는 것이 요점이고, 실제 적용은 별도 확인 후.

> **`cases/`와 `golden/`에 같은 사업(괴산 금신리)이 나오는 건 중복이 아니다.** `golden/`엔 **정답**, `cases/`엔 **입력과 우리 생성물**이 들어간다. 이 짝이 존재하는지가 곧 검증 대상 판별 기준이다 (§2 ②).

## 4. 경로 스코핑 설계

| rule | `paths:` | 로드되는 순간 |
|---|---|---|
| `common.md` | (없음) | 항상 |
| `hwpx.md` | `engine/**`, `templates/**` | 엔진·베이스 문서 만질 때 |
| `small-env/_category.md` | `cases/small-env/**`, `templates/small-env/**`, `golden/small-env/**` | 이 카테고리 작업 전반 |
| `small-env/noise-vib.md` | `cases/small-env/*/noise-vib/**`, `cases/small-env/*/vars/noise-vib*`, `templates/small-env/noise-vib*`, `golden/small-env/*/noise-vib*` | 소음진동 파트만 |

> **세 루트가 같은 계위를 쓴다** — `{루트}/{카테고리}/{사업}/{파트}` (단 `templates/` 는 사업 자리가 없다). 덕분에 파트 rule의 경로 패턴을 기계적으로 만들 수 있고, 카테고리가 경로에 박혀 있어 **파트 이름이 카테고리 간에 겹쳐도 섞이지 않는다** (예: 소규모환경의 `noise-vib` 와 환경영향평가의 `noise-vib` 는 규칙이 다르다). 사업 자리는 항상 `*` 이므로 §2 ①대로 한글이어도 무방하다.

**설계 규칙 3가지**

1. **파트 경로 패턴에 `engine/**` 를 넣지 않는다.** 엔진은 파트 무관이어야 하고, 넣으면 파트가 늘 때마다 스크립트 하나 열 때 전 파트 rule이 딸려온다. (PoC의 `scripts/generate_hwpx*` 경로 패턴이 정확히 이 상태였다.)
2. **파트 고유 정보는 코드가 아니라 `cases/{카테고리}/{사업}/vars/` 와 rule에 둔다.** 1번이 성립하려면 이게 선행돼야 한다 — `knowledge_architecture.md` §3 ①문서조립의 "답변파일을 템플릿과 분리".
3. **`_archive/**` 에는 어떤 rule도 걸지 않는다.** 옛 지식이 컨텍스트에 새어 들어오면 안 된다.

파트가 수십 개로 늘어도 컨텍스트엔 **공통 + 카테고리 + 해당 파트 1개**만 들어온다.

## 5. 런타임 동작 흐름 — 신규 사업 1건이 들어왔을 때

§3(구조)·§4(경로 패턴)가 실제로 어떻게 맞물리는지, **신규 사업 "홍성 갈산리 태양광 · 소음진동"** 을 예로 순서대로 따라간다.

### 0단계 — 세션 시작 (사용자가 말 걸기 전)

```
컨텍스트:  CLAUDE.md  +  common.md            ← paths 없음 = 무조건 로드
대기 목록: hwpx.md · _category.md · noise-vib.md · air-quality.md · …
```
이 시점엔 파트 지식이 **하나도 없다.** 대기만 한다.

### 1단계 — 사용자 자료를 규칙에 맞는 자리에 놓는다

```
cases/small-env/홍성_갈산리/input/사업개요.txt
                                  환경질측정_보고서.txt
```

**여기가 핵심.** 이 파일을 여는 순간 경로가 `cases/small-env/**` 에 매칭 → **`_category.md` 자동 주입.**
Claude가 "카테고리 규칙을 읽어야지"라고 판단해서가 아니라 **파일을 연 결과**다 (§1 오해 참조).

### 2단계 — `/generate-report small-env noise-vib`

스킬(절차)이 로드되어 **순서를 지휘**한다: 인풋 읽기 → 용도지역 확인 → 변수 추출 → 계산 → 엔진 실행.
변수를 뽑기 **전에** 파트 규칙이 필요하므로, 스킬이 `rules/small-env/noise-vib.md` 를 **명시적으로 읽으라고 지시**해 앞당긴다. (경로 매칭으로도 3단계에서 걸리지만, 그때는 이미 늦다.)

```
컨텍스트: CLAUDE.md + common.md + _category.md + noise-vib.md + 스킬
```
→ 필요한 지식이 다 모였고, **대기질·수질 규칙은 여전히 안 들어와 있다.**

### 3단계 — 변수 추출 → `vars/` 에 기록

| 필요한 것 | 출처 | 언제 들어왔나 |
|---|---|---|
| 측정값 위치 (L941~) | `noise-vib.md` 변수표 | 2단계 |
| 계획관리지역 → 소음환경기준 '다' | `common.md` 매핑표 | 0단계(상시) |
| 합성소음도 공식 | `noise-vib.md` | 2단계 |
| "저감량 단순 감산 금지" | `noise-vib.md` 오류 레지스트리 | 2단계 |

```
cases/small-env/홍성_갈산리/vars/noise-vib.json
```
→ `cases/small-env/*/vars/noise-vib*` 매칭 (이미 컨텍스트에 있으므로 재주입은 안 됨 — §1 중복 제거).
**이 파일이 `knowledge_architecture.md` §3 ①문서조립의 "답변파일"** 이다. 사업 데이터가 코드가 아니라 데이터로 분리된 실물.

### 4단계 — 생성 엔진 실행 (Windows)

```
engine/generate.py        ← 열면 engine/** 매칭 → hwpx.md 자동 주입 (한글 API·함정)
  입력: templates/small-env/noise-vib.hwpx          (빈칸 뚫린 베이스 문서)
        cases/small-env/홍성_갈산리/vars/noise-vib.json
  출력: cases/small-env/홍성_갈산리/noise-vib/output.hwpx
```
**엔진은 파트를 모른다.** 베이스 문서 + vars 를 받아 채울 뿐이라 대기질도 같은 엔진을 쓴다 (§4 설계규칙 1의 이유).

### 5단계 — 검증

`/validate-report`. **여기서 처음이자 유일하게 `golden/` 을 연다.**
신규 사업은 정답이 없으므로 실제로는 사람이 검토하고, **`golden/` 에 짝이 있는 사업(괴산 금신리)** 에서만 자동 비교가 성립한다.

> **1~4단계 내내 `golden/` 은 한 번도 열리지 않는다.** 그것이 "정답지 참조 금지"의 실물이다.

### 한 장 요약

```
사용자 자료 → cases/small-env/홍성_갈산리/input/
                     │
                     ├─(경로 매칭)→ _category.md 자동 주입
                     ▼
              /generate-report ─(스킬 지시)→ noise-vib.md 로드
                     ▼
              변수 추출 → vars/noise-vib.json
                     ▼
              engine/generate.py ─(경로 매칭)→ hwpx.md 자동 주입
                     │
     templates/small-env/noise-vib.hwpx (베이스 문서)
                     ▼
              cases/.../noise-vib/output.hwpx
                     ▼
              /validate-report  ← 여기서만 golden/ 접근
```

### 지식이 들어오는 경로는 3가지뿐

| 방식 | 예 | 보장 수준 |
|---|---|---|
| **상시** (paths 없음) | `common.md` | 항상 |
| **경로 매칭** (자동) | `_category.md`, `hwpx.md` | 그 폴더를 건드리면 확실히 |
| **스킬 지시** (명시) | `noise-vib.md` 앞당겨 로드 | 스킬을 호출하면 |

경로 매칭이 **안전망**, 스킬이 **순서 지휘**다. 스킬 없이 "이 파일 좀 봐줘" 만 해도 폴더만 맞으면 지식이 따라온다.

> **대기질을 시켰다면** 2~4단계에서 `air-quality.md` 가 들어오고 `noise-vib.md` 는 끝까지 안 들어온다. 파트가 50개가 돼도 같다 — `knowledge_architecture.md` §6 "규모와 무관하게 컨텍스트는 lean"의 실제 모습.

### 단계 4에 들고 갈 것 — 분기 로직 서술 수정

3.5단계 검증(§1 관측 5) 중 괴산 골든셋을 읽다가 발견한 것. 현재 `noise-vib.md` 의 분기 로직은 **"초과 PP 없음 → 단순 구조 / 일부 초과 → 확장 구조"** 로 서술돼 있는데, **괴산은 초과 PP가 0건인데도 최종 저감대책 표(테이블 29)가 그대로 있다.** 규칙에 "원주 템플릿에 있으면 포함 유지"라는 단서가 붙어 있어 결과적으로 틀리진 않으나, **단순/확장이라는 이분법 자체가 오해를 부른다.**

실제 변이는 *표의 유무*가 아니라 **저감 단계 수**(저소음장비 → 분산투입 → 가설방음판넬)로 보인다. 7장르 재편집의 "분기" 장르에서 이 축으로 다시 쓸 것. → 확정은 §7의 `golden/small-env/_variants.md`(사업 간 변이표)를 채우면서.

### ⚠️ 3.5단계 — 빼먹으면 스코핑이 조용히 죽는다

폴더를 옮겨도 **파일 안에 적힌 경로는 따라오지 않는다.** 특히 rule의 `paths:` 가 옛 폴더를 가리키면 **에러 없이 그냥 로드가 안 된다** (§1의 "조용한 실패"가 우리 이행 과정에서 재현되는 것). 3단계 직후 반드시 수행한다.

| 파일 | 고칠 것 | 옛 → 새 |
|---|---|---|
| `.claude/rules/hwpx.md` | `paths:` | `scripts/**` → **`engine/**`** |
| `.claude/rules/small-env/noise-vib.md` | `paths:` | `tests/소음진동/**` 외 → §4 표 |
| `.claude/skills/generate-report/SKILL.md` | 본문 경로 | `tests/{섹션}/input/` → `cases/{카테고리}/{사업}/input/` |
| `.claude/skills/validate-report/SKILL.md` | 본문 경로 | `tests/{섹션}/output`·`expected/` → `cases/…/{파트}/`·`golden/…` |
| `engine/generate.py` | 템플릿·출력 경로 | `templates/원주_…hwpx` → `templates/small-env/noise-vib.hwpx` 외 |
| `catalog/build_catalog.py` | 입출력 경로 (6곳) | `docs/nas_*` → `catalog/data/`·`catalog/review/` |
| `catalog/synology_filestation.py` | docstring 예시 | `docs/nas_index.json` → `catalog/data/…` |

**검증**: 3.5단계 후 세션을 재시작하고, `cases/small-env/괴산_금신리/…` 파일을 열어 `noise-vib.md` 가 실제로 주입되는지 확인한다 (§1 실무 함의 — 그 rule을 손으로 먼저 읽으면 테스트가 무효가 되므로 주의).
