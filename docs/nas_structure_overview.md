  전수 규모 폴더 7.4만+(`0. 기타자료` 심층 6.7만+ 별도) · 파일 73만+ · `(본안)` 파트 보고서 8,047건.
- **먼저 올라온 재해에서도 "예외처럼 보이는" 케이스**가 있는데, 열어보니 실수가 아니라 **수기·시간누적 시스템에서 불가피하게 생기는 구조적 특성**(다중폴더·임시번호 등)이었다.

- 카탈로그 **v1 = 290 유니크 사업** (후보 폴더 301개 클러스터링, 정본 선택·정규화·검수 플래그 자동). **잠정본** — 전수 스냅샷 기반 v2 는 업로드 완료 후 재빌드.

## 1. 어떻게 파악했나 (방법)

NAS 웹(QuickConnect) 화면은 동적 로딩이라 눈으로 훑기엔 느리고 누락이 생긴다. 그래서 **File Station API로 폴더 트리를 통째로 긁어**(파일 내용은 안 받고 **목록·크기만**) 정적 데이터(`nas_index.json`)로 만든 뒤 분석했다.

- **파일 다운로드 없음** — 7만+ 폴더/73만+ 파일이어도 결과는 텍스트 (압축 ~10MB).
- **재현 가능** — 같은 명령이면 누구나 동일 트리를 다시 뽑는다.
- 자격증명은 `~/.synology.env`(git 제외)에 분리.
- 상세 명령·제약 → **부록 A-1**.

## 3. 정리된 재해에도 "불가피한 구조적 특성"이 있다 (오류 아님) ⭐

`0.평가서/재해`에서 문제처럼 보이는 4가지가 나오는데, 실물을 열어보면 **실수가 아니라 수기·시간누적 시스템에서 자연히 생기는 특성**이다. 자동화는 이를 **흡수하도록 설계**했다. 현업 처리와 대조하면:

| 구조적 특성 | 불가피? | 현업 방식 | 우리 처리 |
|---|:--:|---|---|
| **한 사업 다중폴더** — `재21-10` 두 폴더 (원주 무실지구 도시개발: 보류된 행정본 + 실제 검토본, 실물 확인) | ✅ | 두 폴더 공존 | `다중폴더` 태그 → 같은 사업으로 확정 |
| **임시·외주 번호** — `재26-99`(정식번호 미정), `재26-외NN`(외부 의뢰) | ✅ | 관례로 사용 | 그들 뜻대로 `임시번호`/`외주`로 해석 (충돌 아님) |
| **한 실사업 여러 번호** — 벨라스톤 = `재23-09`+`재24-22`+`환24-30`+`환26-01` (단계별 계약) | ✅ | 번호별 폴더로 흩어둠 | `상위실사업` 링크로 묶음 |
| **빈 셸** — 이름만, 파일 0 (진행 중) | ✅ | 채우는 중 | `빈셸` 태그 + 실물을 연도폴더에서 연결 |

> 4가지 모두 **오류가 아니라 자연 발생 상황**이다. 그래서 "완전함"은 이름·번호만으론 증명 못 하고, **애매한 것만 플래그로 사람에게** 넘긴다.

## 4. 저장소는 아직 "업로드 중"이라 어질러져 있다 (정착된 문제 아님)

현재 NAS가 지저분해 보이는 건 정착된 체계가 망가진 게 아니라, **여러 로컬 소스에서 올리는 중이라 생기는 과도기**다. 관측된 것:

| # | 현상 | 근거 |
|:-:|---|---|
| 1 | 번호체계가 소스마다 다름 | 2018=`환18-NN`/2021~22=순번/2023~24 혼재 |
| 2 | 동일 사업 중복 업로드 | 수청리 4곳·벨라스톤 9곳 (로컬 사본이 여러 위치에) |
| 3 | 빈 껍데기 폴더 | 이름표만, 파일 0 (아직 안 올라왔거나 중지중) |
| 4 | 비표준·임시 폴더명 | `ㅎㅈ`,`폴더모음` |
| 5 | 정리 축 혼재 | 연도·담당자·아카이브 공존(§2) |

> 이건 **"풀어야 할 정착된 레거시"가 아니라 업로드 과도기**다. → **참조 구조를 정해두고 올려가면** 자연히 정돈된다.
>
> **NAS 안에 이중 복사/백업은 불필요** — 원본이 각자 **로컬**에 있어 그 자체가 백업 역할을 한다. 우리가 걱정했던 "이동/삭제 정책" 부담도 크게 준다. (로컬→NAS 정리 방식만 담당자와 맞추면 됨: `reorg_strategy.md` §7)

## 5. 우리 제안 — 정규화 트리(참조) + id 인덱스 + 검수 워크리스트

**핵심 판단**: 정리의 병목은 "누가 폴더를 옮기냐"가 아니라 **"폴더 이름만으론 올바르게 정리할 수 없다"**(파일 실체 + 실무 지식 필요)는 점이다. 그래서 기계가 목록화·탐지·후보추정을 하고, **최종 정리 방식·판단은 현업이** 가져간다.

우리가 만든 건 **같은 카탈로그의 세 산출물**이다:

| 산출물 | 누구용 | 무엇 |
|---|---|---|
| **정규화 폴더트리** — `nas_catalog_review.md` | **현업(참조)** | 영역→종류로 **이렇게 정리해보면 어떨지 참조 예시** (강제 목표 아님) + 검수 플래그 |
| **id 인덱스** — `nas_catalog.json` | **개발** | 우리 고유 `id` + 실물 `위치경로` (자동화가 실물을 찾아감) |
| **검수 워크리스트** — `nas_catalog_todo.md` | **현업/우리** | 사람 판단 필요 항목만(영역미상·중복후보 등) 체크리스트 |

> **어떻게 만드나**: 전체 폴더 나열 → **클러스터링으로 중복 제거** → **정본(진짜 최종본) 자동 선택** → 정규화 이름. 규칙 상세는 `reorg_strategy.md` §3, 코드는 `scripts/build_catalog.py`.
>
> **왜 종류 계층을 넣나**: 그들 `0.평가서`는 영역 밑에 프로젝트가 평평하게 나열(재해 79·환경 125건)이라 훑기 어렵다. 우리는 그 사이에 **종류 계층**(소규모환경/재해영향평가…)을 넣어 **스캔 편의 + 자동생성 단위(종류별 템플릿)와 정렬**했다. 단, 종류는 json엔 **태그**로만 있어 **2단(그들 방식)으로도 렌더링 가능** — 강제 아닌 참조.

> **왜 트리 말고 인덱스(json)도 필요한가?** 트리는 사람이 읽는 납작한 뷰라 "이름 + 플래그"까지가 한계다. 자동화는 그 이상이 필요하다 — **실물 파일이 어디 있는지**(`위치경로`·`정본경로`)와, 영역·종류·상태를 **개별 필드로 질의·필터**하는 것. 이건 트리로는 못 담는다. (`id`는 이름이 바뀌거나 충돌해도 안 깨지게 하는 **불변 손잡이**일 뿐, 목적은 메타데이터 자체.)

→ 실무자는 이 **참조안을 검수·취사선택**하면 되어 맨손 정리보다 빠르다. **정답이 아니라 출발점**이니 자기 관례에 맞게 조정하면 된다. (설계·스키마·담당자 질문: **`reorg_strategy.md`**)

**현황 (v1 전수)**: 전체 폴더 301개(0.평가서 166 + 연도 135)를 클러스터링 → **유니크 사업 290건**. 정본은 내용 우선으로 자동 선택, 검수항목은 플래그로 표면화(실물없음 86·번호미상 76·중복? 39·폐기? 3·영역확인 1·미분류 74). **플래그 뜻+건수 전체 표는 `nas_catalog_review.md` 상단**, 판단 워크리스트는 `nas_catalog_todo.md`. dedup·정본선택 규칙은 `reorg_strategy.md` §3.

# 부록 A — 근거 & 방법 상세

## A-1. 수집 방법 (File Station REST API)

| 단계 | 도구/명령 | 산출물 |
|------|----------|--------|
| ① 인증 | `SYNO.API.Auth` 로그인 → 세션 SID | — |
| ② 트리 수집 | `SYNO.FileStation.List` 재귀 호출 (depth 3) | `nas_index.json` |
| ③ 개별 확인 | 특정 폴더만 추가 조회 (예: `환18-03`) | 사업자/보고서 위치 확인 |
| ④ 분석 | 로컬 JSON을 파이썬으로 집계 | 이 문서 · 카탈로그 |

```bash
# 로그인 테스트 + 공유폴더 목록
python3 scripts/synology_filestation.py shares
# 트리 추출 (목록·크기 메타데이터만, 파일 내용 안 받음)
python3 scripts/synology_filestation.py tree "/backupenv" --depth 3 --json docs/nas_index.json
# 개별 보고서 다운로드 (100MB 초과 시 확인)
python3 scripts/synology_filestation.py download "/backupenv/2024/24-17.../보고서.hwp" --dest raw_data/nas/
```
- **제약**: 관리자 권한 계정이 아니면 접근 가능한 공유폴더만 보인다(현재 `backupenv`,`docker`). `#recycle`(휴지통)은 차단(code 407).

## A-3. 사전 미팅 가설 검증

담당자 청취: **"영역은 재해·환경·도시·인허가 4개. 연도별 정리 완료된 건 환경·재해 2개."**

**`0.평가서` 정리 방식** — 연도 하위폴더가 아니라 관리번호 접두:
```
환24-17 평창 수청리 태양광발전소 소규모환경영향평가(㈜용덕쏠라)
└─┬─┘ └──── 사업명/위치 ────┘└─평가종류─┘└사업자/발주처┘
```
- 관리번호 연도분포: 재해 `재19~26` / 환경 `환24~26`만.

**가설 재판정**:
- "정리 완료 = 환경·재해 2개" → **재해만 정리 형태**. 환경은 자료 자체는 대량 존재하나(신규는 `0.평가서/환경` 환25·26, 과거분은 `0. 기타자료` 아카이브·개인 폴더·연도폴더) 정리 미완.
- **도시·인허가는 독립 영역 아님** — 도시개발/지구단위/가로주택정비 사업이 *재해·환경 평가*를 받아 재/환 폴더에 편입(예: `환24-05 춘천 장학리 도시개발사업 환경 및 재해영향평가`); 인허가(비점오염원신고·배출시설허가·수질오염총량 등)는 *환경* 폴더에 흡수. → 회사가 4개로 *인식*하되 산출물은 **재해·환경으로 귀결**.

**보고서 종류 빈도** (`0.평가서` 프로젝트명 기준):
| 환경 | 건수 | 재해 | 건수 |
|---|:--:|---|:--:|
| 환경영향평가(본) | 49 | 재해영향평가 | 51 |
| 소규모환경영향평가 | 48 | 소규모재해영향평가 | 47 |
| 사후환경영향조사 | 10 | 재해영향성검토 | 4 |
| 환경보전방안검토 | 7 | 우수유출저감대책 | 3 |
| 비점오염원/배출시설 신고·허가 | 7 | | |
| 전략·환경성검토·수질오염총량 | 4 | | |

> ※ 한 사업이 환경+재해를 동시 수행하는 경우가 많아 폴더 간 교차 존재.
