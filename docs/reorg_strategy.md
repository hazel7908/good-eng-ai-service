# NAS 정본 카탈로그 & 정리 참조 전략 (초안)

> **작성일**: 2026-07-21 · **상태**: 초안 (v1 전수 반영) — 검토 후 취사선택
> **전제 문서**: 저장소 구조 파악은 [`nas_structure_overview.md`](./nas_structure_overview.md) 참조
> **한 줄 요약**: 파일을 물리적으로 복사·이동하지 않고, **사업 단위의 "정본 카탈로그"(메타데이터)** 를 만들어 회사에 참조로 제시한다. 기계가 대량·기계적 정리를 하고, 실무자는 판단·취사선택만 한다.

## 1. 왜 하는가 (문제 정의)

- 이 NAS(`/backupenv`)는 **우리 자동생성 프로젝트가 쓸 입력 데이터 전체**다. 정합성이 깨지면 자동화의 신뢰도가 무너진다.
- 그런데 원래 각자 로컬에 있던 파일을 NAS로 **올리는 중**이라, **불가피한 구조적 특성 + 업로드 과도기의 어질러짐**이 있다 (근거: `nas_structure_overview.md` §3~4).
- 정리 체계는 아직 미확정이고 **재해만 거의 올라온** 상태다. 수작업 + 이름만으론 올바르게 정리하기 어렵다(환경은 셸 1/87).

**핵심 판단**: 정리의 병목은 "누가 폴더를 옮기냐"가 아니라 **"폴더 이름만으론 올바르게 정리할 수 없다"**(파일 실체 + 실무 지식 필요)는 점. 그래서 역할을 나눈다.

| 기계(우리)가 할 일 | 사람(실무자)이 할 일 |
|---|---|
| 전수 목록화, 중복·빈셸·다중번호 **탐지**, 최종본 **후보 추정**, 참조 트리·카탈로그 **생성** | "이게 최종본이다 / X=Y다" **판단**, 목표 구조·관례 **확정**, 참조안 **취사선택·활용** |

## 2. 커버 범위 — NAS 전체를 분류하되, 초점은 평가서 산출물

이 NAS엔 재해·환경 평가서 말고도 여러 종류가 섞여 있다 (folder-name census, 6,327폴더 대상):

| 계층 | 종류 (예시·대략 건수) | 카탈로그 처리 |
|:--:|---|---|
| **① 평가서 산출물** | 환경영향평가·소규모환경(101)·전략(13)·자연환경(6)·사후조사(27)·환경보전방안(18)·환경성검토(38) / 재해영향(47)·소규모재해(48)·우수유출·풍수해정비 | **깊게 정리** (자동화 타깃) |
| **② 인허가류** | 비점오염원신고(6)·배출·배수설비허가(12)·수질오염총량(8) | **깊게 정리** |
| **③ 부수 기술검토** | 에어모드(대기확산)·경관성·교통성·토지적성·표고경사·지질조사·정도검사 | **원칙상 상위 프로젝트의 내부요소** (단독계약이면 예외적으로 독립 사업) |
| **④ 행정/영업** | 견적·발주·계약·공문 | **얕게 태깅만** (범위 밖, 존재만 인지) |

> ⚠️ census 주의: `계약(208)`·`견적(195)`·`에어모드(167)`는 별개 사업이 아니라 **프로젝트마다 반복되는 하위폴더** 이름이라 부풀려진 수치. 프로젝트 레벨 개수와 직접 비교 불가.

**미팅 4영역(재해·환경·도시·인허가) 대조**: 재해=①재해군, 환경=①환경군, 인허가=②, **도시=독립 없음(①에 흡수)**. 그 외 ③④는 미팅에 없던 추가 콘텐츠.

**결론**: 카탈로그는 **NAS 전체를 100% 포함**(버리는 것 없음). 티어는 *"얼마나 깊이 다루나"* 의 차이일 뿐:
- **①②** = 프로젝트 **엔트리로 완전 구조화** (자동화 초점)
- **③** = 엔트리 **안의 구성요소로 종속** (독립 엔트리 아님, 단독계약이면 예외)
- **④** = **포함하되 내용분석은 안 함** (폴더 태그만; "범위 밖" = 빼는 게 아니라 안 파헤침)

## 3. 데이터 모델 — "사업(프로젝트)"이 원자 단위

> ⭐ **가장 중요한 원칙**: 커버 범위(티어 ①②③④)와 카탈로그 계위는 **다른 축**이다. 티어는 프로젝트에 붙는 **태그**이고, 카탈로그의 단위는 **사업**이다. **한 사업은 절대 여러 티어로 쪼개지지 않는다.**

- ③기술검토·④행정은 카탈로그에서 **독립 노드가 아니라 프로젝트의 내부 구성요소**로 들어간다 → 프로젝트는 통째로 유지.
- **커버 범위** = "무엇이 있나"의 분류 뷰(통계/태그). **카탈로그 계위** = "사업 단위로 묶은" 구조 뷰. 같은 데이터의 다른 뷰.
- **표현 vs 실물**: 카탈로그는 프로젝트를 **폴더 수준으로 요약 표현**(안의 파일을 하나하나 열거하지 않음). 실물은 프로젝트 폴더 단위(③④ 포함)로 다뤄지고, 만약 재배치한다면 **폴더 통째로**. → **표현은 요약, 실물은 폴더 통째.**

### 까다로운 경계 2가지 (분류 시 판단 필요)

1. **같은 이름이 독립 사업일 때도, 내부 요소일 때도 있음**
   - `경관성검토`·`비점오염원신고`가 **단독 계약** → 독립 프로젝트 노드
   - 큰 평가서 **안의 하위폴더** → 그 프로젝트의 내부 요소
   - 구분 기준: **독자 관리번호/계약 존재 여부** (규칙 + 일부 사람 판단)
2. **한 실사업 = 여러 관리번호** (벨라스톤 = 재23-09/재24-22/환24-30/환26-01)
   - 원자 단위는 **관리번호(건별 용역)**, 그 위에 **상위 실사업**으로 묶는 링크
   - → over-split(쪼개짐)도 over-merge(뭉개짐)도 방지

### 중복 해소 & 정본 선택 규칙 (v1 핵심 자산) ⭐

같은 사업이 여러 곳(0.평가서·연도폴더·담당자폴더)에 흩어져 있으므로, v1은 **전체 폴더 나열 → 클러스터링(dedup) → 정본 1개 선택** 순으로 유니크 셋을 만든다. (v0는 0.평가서만 척추로 삼았음)

**(1) 그룹핑 — 관리번호만으론 안 됨** (소스마다 번호가 다름)
```
0.평가서: 환24-17 …수청리 태양광 소규모환경
연도폴더: 24-17 …수청리…(완)
kdy:     8. …수청리 태양광(X)
lsy:     5. …수청리(타절)
```
→ **다중 신호로 클러스터**: 번호 코어(`24-17`) + 위치 토큰(`수청리`) + 사업종류(`태양광`) + 사업자.
→ 애매하면 자동 병합 금지, **`병합확인` 플래그**. (over-merge=같은 지명 다른 사업 / under-merge=다르게 명명된 사본)

**(2) 정본 선택 — 우선순위는 "출처"가 아니라 "내용" 먼저** ⭐
"무조건 0.평가서 우선"은 **틀림** — 0.평가서/환경은 대부분 빈 셸이라 가리킬 게 없다. 규칙(우선순위):

| 순위 | 기준 | 이유 |
|:--:|---|---|
| 1 | **실물 최종본 존재** — `2.보고서`에 `(완)` 파일 | 없으면 정본 자격 없음(자동화가 읽을 파일이 실제 거기 있어야) |
| 2 | **superseded 제외** — `(X)`·`(타절)`·`보류` 표식 | 폐기/중단된 사본 |
| 3 | (동점) 출처 순위 or 완성도 | 채워진 0.평가서 > 연도 > 담당자 / 파일 수·최근 mtime |
| 4 | 그래도 애매 | **`정본불명` 플래그** → 사람 |

→ 흔히 **연도폴더가 정본**(풀세트를 담고 있어서). 예: 수청리 = `24-17 연도폴더(완)`가 정본, 0.평가서 빈 셸·담당자 사본(X/타절)은 `위치경로`에만 기록.

**(3) JSON 기록**: `위치경로[]`에 발견된 **모든 출처 보존**(증거) + `정본경로_추정` 1개 지목 + 애매하면 플래그. 트리엔 그룹당 **정규화 이름 1개**.

> 대부분 자동, 플래그된 것만 사람 검수 (9할 기계 + 1할 사람). **이 dedup·정본 판별이 카탈로그의 핵심 가치** — 흩어진 원본에서 "진짜 최종본이 어디"를 자동으로 좁혀주는 부분.

## 4. 카탈로그 스키마 (엔트리 1건 = 관리번호 1건)

```jsonc
{
  "id": "ENG-2024-017",              // 우리가 부여하는 안정적 고유키 (관리번호와 별개, 불변)
  "관리번호": "환24-17",              // 회사 번호 (없을 수 있음 → null)
  "상위실사업": null,                 // 여러 번호가 한 실사업이면 그 그룹키 (예: "벨라스톤CC")

  "사업명": "평창 수청리 태양광발전소 소규모환경영향평가",
  "위치": "강원 평창군 미탄면 수청리 73",
  "사업자": "㈜용덕쏠라",             // 개인명이면 사업주, 업체면 발주처 (구분 태그)
  "사업자유형": "업체",               // 개인 | 업체 | 관공서

  "영역": ["환경"],                   // 다중 가능: ["환경","재해"]
  "보고서종류": ["소규모환경영향평가"],// 다중 가능: ["소규모환경","소규모재해"]
  "티어": "①평가서산출물",
  "상태": "완료",                     // 완료|취하|반려|보류|중지|진행
  "연도": 2024,

  "위치경로": [                       // 이 사업 파일이 실제로 존재하는 모든 경로
    "/backupenv/2024/24-17 평창군 미탄면 수청리 …(완)",
    "/backupenv/0. 평가서/환경/환24-17 …(빈 셸)",
    "/backupenv/kdy/2024/8. 평창군 …수청리 태양광(X)",
    "/backupenv/lsy/3. 소규모환경영향평가/2024/5. …수청리(타절)"
  ],
  "정본경로_추정": "/backupenv/2024/24-17 …(완)",   // 실물이 있는 유일본
  "최종보고서_추정": [                 // 최종 납품본 파일 후보 (heuristic)
    "…/2. 보고서/(본안) 0100 사업의 개요(완) 1-12.hwp",
    "…/2. 보고서/(본안) 0100 사업의 개요(완) 1-12.pdf"
  ],
  "구성요소": ["받은자료","보고서","기타자료","수치지도"],  // 내부 폴더(③④ 포함)

  "플래그": ["환경0.평가서셸_비어있음"],  // 사람 검수 필요 이슈
  "검수상태": "미검수",                // 미검수 | 확인 | 수정필요
  "비고": ""
}
```

### 최종본 후보는 이렇게 잡힌다 (프로젝트 안 `2.보고서`에서만)

프로젝트 폴더 안의 다른 폴더(받은자료·계약·에어모드…)는 **구성요소로 포함만** 되고, **최종본 후보 플래그는 `2.보고서`의 완성 보고서에만** 붙는다:

```
환24-17 …/
├ 0. 받은자료/ · 1. 계약/ · 에어모드/          ✗ 후보 아님 (구성요소로만 포함)
└ 2. 보고서/
   ├ (본안) 0000 표지 및 목차(완).hwp/pdf      ★ 최종본 후보
   ├ (본안) 0100 사업의 개요(완) 1-12.hwp/pdf   ★ 최종본 후보  ← 자동생성 핵심 입력
   ├ (본안) 0200 지역개황(완) 13-44.hwp/pdf     ★ 최종본 후보
   └ (초안) 0100 사업의 개요.hwp                ✗ 제외 (초안본)
```
판별 규칙(heuristic): `(완)`·`(본안)` 표식 + `hwp`+`pdf` 쌍 + `2.보고서` 하위 → 후보. 애매하면 `플래그: 최종본불명`으로 사람에게.

### 다중번호 실사업 예 (벨라스톤 — 4개 엔트리가 1개 상위사업에 링크)

```jsonc
// 4개의 독립 엔트리, 모두 "상위실사업":"벨라스톤CC" 로 묶임
{ "id":"ENG-2023-…", "관리번호":"재23-09", "상위실사업":"벨라스톤CC", "영역":["재해"], "보고서종류":["재해영향성검토"] }
{ "id":"ENG-2024-…", "관리번호":"재24-22", "상위실사업":"벨라스톤CC", "영역":["재해"], "보고서종류":["재해영향평가"] }
{ "id":"ENG-2024-…", "관리번호":"환24-30", "상위실사업":"벨라스톤CC", "영역":["환경","재해"], "보고서종류":["환경영향평가"] }
{ "id":"ENG-2026-…", "관리번호":"환26-01", "상위실사업":"벨라스톤CC", "영역":["환경"], "보고서종류":["환경영향평가(보완)"] }
```

### 필드 자동추출 가능성 (이름·메타데이터 기반)

| 자동(O) | 규칙+검수(△) | 사람 판단(X) |
|---|---|---|
| 관리번호·연도·사업명·위치·사업자·영역·종류·상태·위치경로·구성요소 | 정본경로·최종보고서 후보·상위실사업 링크·티어(경계사례) | "진짜 최종본이 맞나"·"두 폴더가 같은 사업인가" 최종 확정 |

> **v1 실제 출력 vs 위 스키마**: v1 엔트리는 *관리번호 1건*이 아니라 **유니크 사업(클러스터) 1건**이다. 실제 필드 = `id·관리번호·번호코어·정규화이름·원본이름_정본·영역·보고서종류·상태·사업자·사업종류·위치·정본경로_추정·정본출처·위치경로[]·출처수·플래그·검수상태`. 위 스키마의 `티어·구성요소·최종보고서_추정·사업자유형`은 아직 미구현(다음 단계).

## 5. 산출물 3종

1. **정본 카탈로그** (`nas_catalog.json` 기계용 + `nas_catalog_review.md` 트리·검수용) — 위 스키마의 사업 목록. 파일 복사 없음, 재생성 가능 (`scripts/build_catalog.py`).
2. **오류 리포트 / 검수 워크리스트** — 카탈로그에 **플래그로 내장**(실물없음·번호미상·중복?·전부폐기·영역혼재), 그중 사람 판단 항목만 뽑아 **`nas_catalog_todo.md`** 로 별도 체크리스트 생성. **실무자 검수 대상은 이것만.**
3. **(선택) 정리 반영 스크립트** — 이미 올라온 것 중 재배치가 필요하면 "A→B" 안을 코드로 생성, **그들 승인 후 실행**. (업로드 중이라 필수는 아님 — 목표 구조에 맞춰 올리면 대부분 불필요)

## 6. 한계 & 리스크 (정직하게)

- **현재 지도는 depth-3 + 이름·크기만.** 프로젝트 내부 파일(보고서 챕터 등 depth 4~5)·내용은 미수집 → "최종본 판별"은 더 깊이 긁거나 표본 열람 필요.
- **이름 기반 분류의 오류 가능성** — 이미 겪음(발주처↔사업자, 빈 셸). 자동분류는 "후보"이고 검수로 확정.
- **파일을 복사하지 않는 이유** — 물리 복제본은 원본과 어긋나고 관리 부담만 는다. 원본도 각자 로컬에 있어 NAS에 또 복제할 이유가 없다. 그래서 "가리키는 카탈로그"만 만든다.
- **판단 불가 영역** — 관리번호 관례, 목표 구조 합의 여부, 최종본 확정은 담당자만 안다(§7).

## 7. 담당자 확인 질문 (미팅용)

> 전제: 원래 로컬에 있던 파일을 NAS로 **올리는 중**이고 정리 체계는 미확정. 그래서 "이관/이동·삭제/빈 셸 채우기" 같은 질문은 성립하지 않는다.

1. **목표 구조가 합의된 채로 올리고 있나?** — 정해진 정리 체계에 맞춰 업로드 중인지, 각자 방식대로 올리는 중인지. (전자면 우리 트리를 그 체계에 맞추고, 후자면 참조안으로 제시)
2. **관리번호 부여 관례 확인** — 우리 해석(`99`=정식번호 미정, `외`=외주, `사`=사후)이 맞는지.
3. 우리가 만든 **참조 트리·카탈로그**를 검토·활용할 의향이 있는가? 어떤 형태가 쓰기 좋은가?
