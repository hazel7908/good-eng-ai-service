# 지식 아키텍처 설계 — 보고서 자동생성 지식 체계

> **작성일**: 2026-07-23
> **목적**: 전 영역 보고서 자동생성을 위해 쌓을 "지식"(이 보고서는 이렇게 쓴다)을 **어떤 구조로** 담을지 설계. 유사 서비스 조사 + 우리 레포(Claude Code) 특성에 맞춘 결론.
> **읽는 법**: §2(우리 지식 정체) → §3(남들은 어떻게) → §4~6(Claude Code 친화 결론) 순.

---

## 1. 문제 — 지식이 커진다

전 영역(재해·환경·인허가 …)을 다 정리하면 "이 파트는 이렇게 작성한다"는 지식이 **방대**해진다. 아무렇게나 쌓으면 곧 관리 불능. **잘 짜인 지식 구조**를 먼저 설계해야 한다.

핵심 질문 두 개:
1. 우리 지식은 **무슨 종류**인가? (그래야 맞는 구조를 고름)
2. 그걸 **Claude Code에 친화적으로** 담으려면?

---

## 2. 우리 지식의 정체 = "문서 조립(Document Assembly)" 장르

PoC의 `.claude/rules/소음진동.md` 한 파일을 뜯어보면, **한 파트 안에서도 7가지 이질적 장르**가 섞여 있다:

| # | 장르 | 소음진동.md의 실제 예 |
|:-:|---|---|
| ① | **템플릿 구조 매핑** | Table 0~29: 각 표의 내용 → 변경방식 |
| ② | **변수→출처 추출규칙** | 주간평균 → 측정보고서 L945 (분류: O/계산/삽도/X/고정) |
| ③ | **계산 공식** | 합성소음도 = 10·log10(Σ N·10^(SPL/10)) |
| ④ | **분기 로직** | IF 일부 PP 기준초과 THEN 확장구조 |
| ⑤ | **조건부 문구** | 전지점 만족 → "영향 미미할 것" |
| ⑥ | **오류 레지스트리(QA)** | 기준 '나'↔'다' 혼동 → 교훈 |
| ⑦ | **사례 변이표** | 4개 사업의 PP수·기준지역·저감구조 비교 |

→ 이건 **선언적 사실의 목록(온톨로지)이 아니라**, **템플릿 + 데이터 + 계산 + 조건부 포함 + 문체 + 검증**이 얽힌 **문서 생성(조립) 지식**이다. 절차적·계산적·조건부가 핵심.

> ⚠️ 단 이건 **"장르"(지식의 종류)** 규정이다. **실제 설계는 문서조립만 쓰는 게 아니라 ②③도 조합**한다 — §3 끝 "우리 설계 = 조합" 참조.

---

## 3. 유사 서비스는 어떻게 구조화하나 (조사 결과)

우리와 같은 "문서조립 지식"을 다루는 **3계열**을 조사했다.

**용어 구분** — `①②③`은 **장르(분야·기법·표준)** 이름이고, 오른쪽은 그 안의 **실제 제품/도구**다:

| 장르 (분야·기법·표준) | 실제 제품/도구 (예시) |
|---|---|
| ① **문서조립** (Document Assembly) | HotDocs, DocAssemble(오픈소스), Documate(Gavel), Contract Express |
| ② **구조화저작** (Structured Authoring) — 표준: **DITA**(OASIS 규격) | Oxygen XML, MadCap Flare, Adobe FrameMaker |
| ③ **LLM 보고서생성** (기법) | LlamaIndex(프레임워크), 각종 연구 시스템 |

> DITA는 제품이 아니라 **표준**(규격)이고, 나머지 HotDocs·DocAssemble·LlamaIndex는 구체 **제품/프레임워크**다. 우리가 "①문서조립"이라 할 때는 **장르**를 말하는 것 — 특정 제품을 쓰자는 뜻이 아니다.

### ① 문서조립 자동화 — HotDocs · DocAssemble
법률/규제 문서 생성으로 **수십 년 검증된**, 우리와 가장 정확히 같은 문제.
- 템플릿 + **변수(placeholder)** + **계산변수(computed)** + **비즈니스 로직**(IF/THEN, REPEAT 루프 → 언어블록 포함/제외·행 반복)
- **답변파일(입력)을 템플릿과 분리** 저장 → 엔진이 조립
- DocAssemble = **YAML + Python**로 로직 표현
- **교훈**: 우리 ①②③④⑤와 1:1. → **템플릿 / 변수 / 로직 / 입력을 분리**하는 게 정석.

### ② 구조화 저작 — DITA (구조화 콘텐츠)
재사용·규모·규제준수의 정석 (의료·항공·금융 규제문서).
- **모듈형 토픽**(단일 주제) + 맵으로 조립
- **조건부 프로파일링**(하나의 소스에서 변종을 필터링)
- **한 번 정의 → 여러 곳 재사용**
- **교훈**: 우리 3층(공통/카테고리/파트) 재사용의 정답 형태. → 공통을 한 번 정의하고 참조, 변종은 조건부로.

### ③ LLM 보고서 생성 — LlamaIndex · 최신 논문
AI로 보고서 만드는 현대 아키텍처.
- **구조화 출력 스키마**(섹션/블록을 타입 객체로 정의)
- 템플릿을 **실행계획으로 파싱, 섹션→필요정보 매핑**
- **지식베이스를 생성 시점에 읽음** (모델 밖 외부 저장소)
- **멀티에이전트**: researcher(검색) / writer(작성) / editor(검증)
- **분리된 패스**: 변수매핑 → 생성 → 일관성감사 → 검증
- **교훈**: 우리 변수스펙·규칙 = **생성기가 읽는 지식베이스**, 오류레지스트리 = **editor 검증 패스**.

### 수렴하는 패턴
세 계열 모두 **하나의 납작한 파일이 아니라, 장르별 산출물을 분리**한다. 그리고 **재사용을 위해 층(공통↔개별)** 을 둔다.

### ⭐ 우리 설계 = 셋 중 하나가 아니라 **조합** (두 층위로 이해)

혼동 주의: "우리 = 문서조립"은 **장르(지식의 종류)** 이야기지, 설계 전체가 ①만 쓴다는 뜻이 **아니다.** 두 층위로 나눠 보면:

| 층위 | 질문 | 답 |
|---|---|---|
| **장르** | 우리 지식이 무슨 *종류*냐? | **①문서조립 하나** (템플릿+변수+계산+조건부 = 내용물) |
| **설계** | 그걸 어떻게 *구조화·생성*하냐? | **①+②+③ 조합** ↓ |

| 계열 | 우리가 **가져오는** 것 | **안** 가져오는 것 |
|---|---|---|
| ① 문서조립 | **지식 내용틀** (템플릿·변수·계산·조건부·고정/변동) + 엄격 규칙 | 결정론 엔진, 폼입력 방식 |
| ② 구조화저작 | **재사용·층·조건부 변종 사상** (공통/카테고리/파트) | XML 형식주의, 텍스트-only 재사용 |
| ③ LLM보고서생성 | **LLM 엔진 · 지식베이스 로드 · 생성/검증 분리** | 느슨한 규칙·자유서식·환각 허용 |

> **한 문장**: "**①문서조립의 지식을, ②구조화저작식 층으로 재사용하게 담아, ③LLM 에이전트가 읽고 생성한다.**"
> → 그래서 이 문서의 §4(Claude=엔진)는 **③**에서, §8(3층 재사용)은 **②**에서 온 것이다.

## 4. 핵심 전환 — **Claude Code가 곧 생성 엔진**이다

여기서 방향이 한 번 뒤집힌다. 위 시스템들(HotDocs·DocAssemble·DITA)은 **별도 엔진이 소비하는 데이터 구조**를 만든다. 엔진이 템플릿+변수+로직을 읽어 기계적으로 채운다.

**하지만 우리는 Claude Code 자체가 생성 엔진이다.** 그러면:

> 지식은 **"엔진용 데이터(온톨로지/DB)"가 아니라, "에이전트(Claude)가 읽고 추론해서 따르는 지시문 파일"** 이어야 한다.

즉 **정교한 온톨로지를 짜는 게 아니라**, Claude가 컨텍스트로 로드해 그대로 따르는 **마크다운 규칙 + 스킬**이 맞는 형식이다. 그리고 **이 레포가 이미 그 구조로 시작했다** (`.claude/rules/`, `.claude/skills/`).

## 5. 6개 산출물 → 우리 레포(Claude Code) 매핑

문서조립의 *개념*(6산출물)은 채택하되, *형식*은 Claude 네이티브로 표현한다.

| 산출물 (개념) | 역할 | Claude Code 형태 |
|---|---|---|
| **① 템플릿** | 문서 뼈대 (고정골격 + 빈 슬롯) | 레포 안 **파일** (HWPX 템플릿) — 스킬이 채움 |
| **② 변수 스펙** | 각 슬롯: 유형·출처·공식 | **`.claude/rules/{카테고리}/{파트}.md`** (변수표) |
| **③ 로직 규칙** | 분기·조건부문구·행반복 | 같은 파트 rule (분기·문구 표) |
| **④ 공유 컴포넌트** | 공통변수·기준매핑 (재사용) | **`CLAUDE.md`**(핵심원칙) + **`rules/common.md`** |
| **⑤ 사례 라이브러리** | 골든셋 변이표 (few-shot·검증) | 레포 안 **참조 파일** + rule 내 변이표 |
| **⑥ QA 레지스트리** | 오류패턴 (검증) | 파트 rule의 "오류 레지스트리" 절 |
| (절차) | 생성·검증 워크플로우 | **`.claude/skills/generate-report`, `validate-report`** |
| (기술) | 한글 API·포맷 규칙 | **`rules/hwpx.md`** |

**원칙**: `skills = 절차(어떻게 한다)`, `rules = 지식(무엇이 사실이다)`. 골든셋·QA(⑤⑥)는 **생성 입력이 아니라 검증용**으로 분리 → "정답지 참조 금지" 원칙과 정합.

## 6. 규모 해법 — 경로 스코핑(Progressive Disclosure)

§1의 "지식이 커진다" 걱정의 답이 여기 있다. `소음진동.md` 맨 위:
```yaml
paths:
  - "tests/소음진동/**"
  - "scripts/*소음*"
```
→ **소음진동 작업할 때만 그 지식이 컨텍스트에 로드**된다. 대기질 작업 땐 대기질 것만.

**함의**: 카테고리 × 파트로 rule 파일이 수백 개가 돼도, **Claude 컨텍스트엔 "지금 다루는 파트"만** 들어온다. 전체 지식량과 무관하게 컨텍스트는 항상 lean.
- 이건 문서조립 엔진엔 없는, **Claude Code만의 규모 해법**이다.
- 로드 오케스트레이션은 **스킬**(generate-report가 "이 파트면 이 rule 참조")이 담당.

---

## 7. 설계 원칙 5개

1. **파일 = 지식.** 외부 DB/온톨로지 아님. 레포 안 마크다운.
2. **경로 스코핑 + on-demand 로드.** 컨텍스트 항상 lean → 규모 무한 확장.
3. **마크다운 우선** (Claude가 표·산문을 추론) **+ 스크립트가 쓸 값만 구조화 블록** (공식·기준표 → `generate_hwpx.py` 등이 소비).
4. **skills = 절차, rules = 지식** 분리.
5. **에이전트에게 주는 지시문**으로 작성 (명령형·명확·"왜/오류패턴" 포함).

## 8. 지식의 3층 구조 (재사용)

DITA의 "한 번 정의 → 재사용"을 우리식으로:

```
① 공통층  (전부 공유)   : CLAUDE.md(원칙) + rules/common.md(기준체계·공통변수) + rules/hwpx.md(기술)
② 카테고리층 (따로)      : rules/소규모환경/… , rules/재해영향평가/… (카테고리 골격)
③ 파트층  (더 잘게, 따로): rules/소규모환경/소음진동.md, /대기질.md, /수질.md …
                           └ 각 파트의 변수스펙·공식·분기·오류 (소음진동.md가 프로토타입)
```
- **공통되는 건 ①에 한 번만** → 중복 제거.
- 파트 rule은 공통 개념을 **참조**(예: "기준체계는 common.md 참조").

## 9. 용어 정리 (헷갈리지 않게)

| 용어 | 뜻 | 언제 |
|---|---|---|
| **골든셋** | 다른 사업의 **완성된 정답 보고서**(실물) | 개발·분석·**검증**용만 |
| **베이스 문서**(템플릿) | 고정골격 + **빈칸(변수 슬롯)** 뚫린 시작 파일 | **상용 런타임**에 채움 |
| **변수 명세서** | 각 빈칸을 *무슨 입력으로 어떻게* 채우나 (규칙) | **런타임**에 Claude가 읽음 |

- 런타임(유저): **베이스 문서 + 변수 명세서 + 새 사업 입력** → 생성. **골든셋은 안 봄.**
- 개발(우리): **골든셋 분석** → 베이스 문서·변수 명세서 도출, **골든셋으로 결과 검증**.

## 10. 현재 상태 vs 목표 (성숙화 경로)

| | 현재 (PoC) | 목표 |
|---|---|---|
| 파트 지식 | `소음진동.md` 1개 (6장르 다 있으나 **산문 한 덩어리**) | 6장르 인식 + 각자 제 형식, 파트별 확장 |
| 공통층 | `common.md`, `hwpx.md` 존재 | 유지·보강 (기준매핑 등) |
| 절차 | `generate-report`, `validate-report` 스킬 존재 | 유지·일반화 |
| 구조화 | 없음 (전부 산문) | **스크립트 소비값**(공식·기준표)만 구조화 블록 |
| 확장 | 소음진동 1파트만 | 소규모환경 전 파트 → 타 카테고리 |

**즉 성숙화 = 새로 짓는 게 아니라, 이미 있는 rules+skills 패턴을 (a) 6장르로 정돈, (b) 카테고리/파트로 확장, (c) 공통층 분리, (d) 스크립트 소비값만 구조화.**
