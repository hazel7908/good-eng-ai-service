# HWPX 보고서 생성 워크플로우

> **이 문서는 절차만 담는다** (`knowledge_architecture.md` §5: `skills = 절차`, `rules = 지식`).
> **수치·공식·기준값·분기 조건을 여기에 적지 않는다.** 전부 파트 rule에 있고, 여기서 복사하면 rule을 고쳐도 이 문서가 낡은 값으로 덮어쓴다.
> ⚠️ 실제로 그런 사고가 있었다 — 이 문서가 *"저감량은 합성소음도 재계산, 단순 감산 금지"* 라고 지시하고 있었는데, 2026-07-29 골든셋 재검증에서 **틀린 것으로 밝혀졌다** (단계별로 방식이 다름). 규칙은 고쳐졌지만 이 문서가 남아 있어 규칙을 덮어쓸 뻔했다.

## 전제 조건

- Windows + 한글 프로그램 설치
- Python 3.10+ (pywin32, Pillow)
- 인풋: `cases/{카테고리}/{사업}/input/` — 사업개요.txt, 환경질측정_보고서.txt
- 삽도 이미지: `raw_data/` 원본 JPG
- **베이스 문서**: `templates/{카테고리}/{파트}.hwpx`
  ⚠️ 없으면 생성 불가. 골든셋에서 도출해야 한다 → `/distill-golden`

## 실행 절차

### 1단계 — 인풋 확인

`cases/{카테고리}/{사업}/input/` 의 파일을 읽는다.

> 이 경로를 여는 순간 `rules/{카테고리}/_category.md` 가 **자동 주입**된다 (경로 스코핑). 카테고리 공통 규칙 — 문서 구조·문체·표기 — 이 여기서 들어온다.

- 사업개요 → 사업명, 위치
- 환경질측정 보고서 → 측정값, **용도지역**
- 용도지역 → 기준 체계 매핑은 `rules/common.md`

### 2단계 — 파트 규칙을 명시적으로 읽는다 ★

```
.claude/rules/{카테고리}/{파트}.md
```

**반드시 이 시점에 읽는다.** 경로 매칭으로도 나중에 걸리지만, 변수를 뽑기 시작한 뒤엔 이미 늦다.

이 파일이 가진 것: 템플릿 표 인덱스 · 변수 출처 · 계산 공식 · 분기 로직 · 조건부 문구 · 오류 레지스트리.

> **판단이 필요한 모든 값의 출처는 이 파일이다.** 이 스킬이 아니다.

### 3단계 — 변수 추출

파트 rule의 변수표에 따라 분류별로 처리한다 (분류 정의는 `rules/common.md`).

| 분류 | 처리 |
|:--:|---|
| **O** | 인풋 텍스트에서 추출 |
| **계산** | 파트 rule의 공식으로 계산 |
| **삽도△** | 추출하되 **실무자 확인 표시** |
| **X** | `[확인 필요]` / `[현장조사 필요]` |
| **고정** | 베이스 문서 그대로 |

원칙:
- **인풋에 없으면 만들어내지 않는다.** 부족하면 `[확인 필요]`
- **인풋 없는 서술은 베이스 문서 텍스트를 유지한다** (임의로 바꾸면 오히려 오류)
- 값은 **원본 텍스트에서 확인**한다. 삽도 추출값은 부정확하다
- 인풋의 **줄 번호에 의존하지 않는다** — 사업마다 파일 구조가 다르다. 항목 이름으로 찾을 것

결과를 `cases/{카테고리}/{사업}/vars/{파트}.json` 에 기록한다.

### 4단계 — 계산

**공식은 파트 rule §계산 공식 절을 그대로 따른다.** 이 문서에 공식을 적지 않는다.

- 중간값을 반올림하지 않는다. **끝까지 실수로 계산하고 마지막에만 반올림**한다
- 계산 결과가 골든셋과 맞는지 확인하려면 → 검증 단계에서. 생성 중엔 `golden/` 을 열지 않는다
- rule이 *"실무자 판단"* 이라고 표시한 값은 **자동 결정하지 말고** 기본값 + 확인 표시로 둔다

### 5단계 — 분기 판정

파트 rule의 분기 로직 절을 적용한다. 조건부 문구도 rule의 문구표에서 고른다.

> rule이 *"골든셋이 갈린다 / 실무자 확인"* 이라고 적은 항목은 **자동 판정 금지.** 기본값을 쓰고 확인 대상으로 표시한다.

### 6단계 — 생성 엔진 실행

```
engine/generate.py
  입력: templates/{카테고리}/{파트}.hwpx
        cases/{카테고리}/{사업}/vars/{파트}.json
  출력: cases/{카테고리}/{사업}/{파트}/output.hwpx
```

**엔진은 파트를 모른다.** 베이스 문서 + vars 를 받아 채울 뿐이라 모든 파트가 같은 엔진을 쓴다.

- `engine/` 을 여는 순간 `rules/hwpx.md` 자동 주입 (한글 API 패턴·함정)
- 실행 전 `taskkill /f /im Hwp.exe`

### 6.5단계 — 채움 내역서 (플랫폼 무관, 생성 필수 산출물)

```
python engine/fill_report.py {카테고리} {파트} {사업}
  출력: cases/{카테고리}/{사업}/{파트}/fill-report.md
```

output.hwpx 를 검토할 실무자용 지도다 — ❓ 직접 채울 것 / ⚠️ 확인할 것 / ✅ 자동 채움.
vars 의 `_확인필요` 배열과 slots 핸들러에서 **기계적으로 렌더링**되므로, 내용이 부실하면
이 문서가 아니라 **vars 의 `_확인필요` 를 고친다** (규약: `rules/common.md` 변수 분류 체계).
validation.md(골든셋 채점표)와 달리 정답 없이 만들어지며, 실무 운영에서 실무자 손에 가는 것은 이쪽이다.

### 7단계 — 검증

`/validate-report` 실행. **`golden/` 은 여기서 처음 열린다.**

## 주의사항

- 🚫 **`golden/` 을 1~6단계에서 열지 않는다.** 실무에는 정답이 없다
- 🚫 **`_archive/` 를 참조하지 않는다.** 옛 지식이 섞이면 해롭다
- ✅ 파트 rule의 **오류 레지스트리를 먼저 확인**하고 같은 실수를 피한다
- ✅ 이 문서에 값을 적고 싶어지면 **rule에 적을 자리인지 먼저 의심한다**
