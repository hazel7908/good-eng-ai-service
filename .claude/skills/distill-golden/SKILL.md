# 골든셋 증류 — 완성 보고서에서 지식을 뽑아낸다

> **이 스킬은 개발용이다.** 보고서를 만드는 게 아니라, **보고서를 만들 규칙을 만든다.**
> `golden/` 을 정면으로 여는 유일한 절차 두 개 중 하나다 (다른 하나는 `/validate-report`).
>
> **산출물 3개**:
> 1. `.claude/rules/{카테고리}/{파트}.md` — 파트 지식 (7장르)
> 2. `golden/{카테고리}/_variants.md` — 사업 간 변이표
> 3. `templates/{카테고리}/{파트}.slots.md` — 베이스 문서 빈칸 명세

## 언제 쓰나

- 새 파트를 시작할 때 (예: 대기질)
- 새 카테고리를 시작할 때
- 기존 규칙이 의심스러울 때 — 특히 **`(1/5)` 항목이 규칙으로 굳어 있는지** 점검

---

## 🚨 제1원칙 — 한 건에서 일반화하지 않는다

**이 스킬이 존재하는 이유가 이것이다.**

2026-07-29 재검증에서 `noise-vib.md` 의 규칙 3개가 틀린 것으로 드러났다. 전부 **괴산 한 건만 보고 쓴 것**이었다:

| 틀린 규칙 | 실제 |
|---|---|
| 주거 진동 기준 70 | **65** (4/5). 괴산은 자체 불일치까지 있었다 |
| 목표기준 지역 문자를 용도지역에서 유도 | 4/5는 **'가' 고정**, 용도지역 무관 |
| 저감량 = 합성 재계산 | ①만 재계산, **②는 단순 감산** |

> **규칙에는 반드시 관측 건수 `(n/5)` 를 적는다.** `(1/5)` 는 법칙이 아니라 그 사업의 우연일 수 있다.

## 실행 절차

### 1단계 — 골든셋 확보 상황 점검

```bash
ls golden/{카테고리}/*/
```

| 건수 | 판단 |
|:--:|---|
| 1건 | ⚠️ **규칙을 쓰지 말 것.** 무엇이 일반이고 무엇이 우연인지 구분 불가 |
| 2~3건 | 변이 축은 보이나 다수결이 약하다. 전부 `(n/N)` 표기 필수 |
| 4건+ | 규칙 도출 가능 |

**텍스트가 없으면 먼저 추출**한다:
```bash
python engine/extract.py golden/{카테고리}/{사업}/원본.hwpx --output golden/{카테고리}/{사업}/{파트}.txt
```

### 2단계 — 구조 파악 (⑦ 변이표 먼저)

**규칙보다 변이표를 먼저 만든다.** 무엇이 사업마다 다른지 알아야 무엇을 변수로 뽑을지 정해진다.

전 사업에서 같은 항목을 **기계적으로** 뽑아 나란히 놓는다:

```bash
for f in golden/{카테고리}/*/{파트}.txt; do
  echo "════ $(basename $(dirname $f))"
  grep -nE '<관심 패턴>' "$f" | head
done
```

> ⚠️ **기계 추출 결과를 그대로 믿지 말 것.** 정규식이 법령 표 텍스트까지 잡아 엉뚱한 값이 나온다. 반드시 **원문 줄을 눈으로 확인**한다. 실제로 첫 집계에서 `초과` 로 검색해 5건 모두 0으로 잘못 나왔다 — 보고서 표기는 `상회` 였다.

축을 정리해 `golden/{카테고리}/_variants.md` 에 쓴다:
- 전체 비교표 (사업 × 항목)
- 축별로 읽기 — **무엇이 무엇을 결정하는가**
- ⚠️ **단일 사업에서 잘못 일반화된 규칙** 절 (있으면)
- 표기 변이 (같은 뜻, 다른 형태)

### 3단계 — 7장르로 분류

`knowledge_architecture.md` §2. 골든셋에서 본 것을 장르별로 나눈다.

| 장르 | 무엇을 찾나 |
|:--:|---|
| ① 템플릿 구조 | 표 순서·인덱스, 어느 표가 유지/치환/계산인가 |
| ② 변수 → 출처 | 각 값이 어느 인풋 파일 어디서 오는가. 분류(O/계산/삽도△/X/고정) |
| ③ 계산 공식 | 수식. **골든셋 실측값으로 역산해 검증할 것** |
| ④ 분기 로직 | 사업마다 구조가 갈리는 지점 |
| ⑤ 조건부 문구 | 조건에 따라 달라지는 문장 |
| ⑥ 오류 레지스트리 | (검증에서 채워진다. 처음엔 비어 있어도 된다) |
| ⑦ 변이표 | → `_variants.md` (2단계) |

### 4단계 — 공식은 반드시 역산 검증 ★

**수식을 골든셋에서 읽었다고 믿지 말 것.** 실제 출력값에서 거꾸로 계산해 맞는지 확인한다.

```python
# engine/calc.py 의 self_test() 패턴을 따른다
# 골든셋 여러 사업 × 여러 행으로 검증해야 우연한 일치를 걸러낸다
```

이렇게 해서 이전 규칙의 **산수 오류**(`10log10(10^7.00+10^7.49)` 를 75.7로 적었으나 실제 76.1)를 찾아냈다.

- 중간값을 반올림하지 않는다. 끝까지 실수로 가고 마지막에만 반올림
- 검증 대상 행은 **거리·시설 종류가 다양하게** 고른다

### 5단계 — 카테고리 공통층 분리

여러 파트에 공통인 것은 `{파트}.md` 가 아니라 `{카테고리}/_category.md` 로 뺀다.

| 공통층에 갈 것 | 파트층에 남을 것 |
|---|---|
| 문서 3단 구조 (가/나/다) | 그 파트의 표 인덱스 |
| 문체·종결어미 | 그 파트의 변수·공식 |
| 표기 규칙 (가운뎃점 등) | 그 파트의 분기 |
| 머리글/바닥글 | |

### 6단계 — 베이스 문서 빈칸 명세

`templates/{카테고리}/{파트}.slots.md` 를 만든다. **Windows 작업을 기계적으로 만드는 것이 목적**이다.

- **토큰 이름 = `engine/generate.py` 핸들러의 반환 키.** 어긋나면 치환이 조용히 실패한다
- 각 토큰에 **원본의 어느 문자열을 대체하는지 + 줄 번호**
- **표는 빈칸을 뚫지 않는다** — 엔진이 앵커 문자열로 셀을 찾으므로 지우면 실패
- 같은 토큰이 여러 곳이면 전부 표기

### 7단계 — 엔진 핸들러 추가

```python
# engine/generate.py
PART_HANDLERS = {
    "noise-vib": (slots_noise_vib, tables_noise_vib),
    "{새 파트}": (slots_xxx, tables_xxx),      # ← 추가
}
```

**엔진 본체는 건드리지 않는다.** 파트 고유 로직은 핸들러 안에만 둔다.

계산은 `engine/calc.py` 에 파트별 상수·함수를 추가하고 `self_test()` 에 검증 행을 넣는다.

## 완료 기준

- [ ] `_variants.md` 에 전 사업 비교표가 있다
- [ ] 파트 rule의 **모든 항목에 `(n/N)`** 이 붙어 있다
- [ ] `(1/N)` 항목은 *"실무자 확인"* 으로 표시돼 있다
- [ ] 공식이 골든셋 **복수 사업 × 복수 행**으로 역산 검증됐다
- [ ] `slots.md` 의 토큰 이름이 엔진 핸들러 키와 일치한다
- [ ] 공통층에 갈 것이 파트층에 남아 있지 않다
- [ ] **스킬에 값·공식을 적지 않았다** (`skills = 절차, rules = 지식`)

## 주의사항

- 🚫 **골든셋 값을 `cases/*/vars/` 에 베끼지 않는다.** 검증이 부정이 된다.
  삽도 추출값이 정답과 달라도 **추출값 그대로 둔다** — 그래야 개선 여부를 잴 수 있다
- 🚫 규칙을 고쳤으면 **스킬도 점검**한다 (값이 스킬에 박혀 있으면 잘못된 자리)
- ✅ 파트 rule 재작성 후에는 `/validate-report` 로 재생성·재측정해야 **실제로 나아졌는지** 알 수 있다
