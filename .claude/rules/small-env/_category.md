# 소규모 환경영향평가 — 카테고리 공통 규칙

> **적용 범위**: 이 카테고리의 **모든 파트**가 공유하는 지식. 파트 고유 지식(변수·공식·분기)은 `{파트}.md` 에 있다.
> **위층**: 기준 체계 매핑·품질 기준·변수 분류 체계는 `.claude/rules/common.md`(상시 로드) 참조. 여기서 반복하지 않는다.
> **근거**: 이 문서의 규칙은 골든셋 5건(`golden/small-env/`)에서 **실측**한 것이다. 각 항목에 관측 건수를 `(n/5)` 로 적었다.

---

## 1. 보고서 골격에서 우리가 만드는 자리

소규모 환경영향평가서 전체 중 우리가 생성하는 것은 **제7장의 개별 파트**다.

```
제7장 환경 현황, 환경에 미치는 영향의 조사․예측․평가 및 환경보전방안
  └ 7.2 …
      ├ 7.2.2  대기질        ← 미착수 (Phase 2)
      ├ …
      └ 7.2.7  소음․진동      ← noise-vib.md
```

**확인된 것** (5/5): 제7장 제목 문자열, `7.2.7 소음․진동`, 그리고 소음진동편이 대기질을 상호참조한다는 사실 — `주) 투입대수 산정내역 : 본 서 7.2.2 대기질편 참조` (4/5).

> ⚠️ **전체 목차는 아직 확정되지 않았다** (`repo_restructure_plan.md` §10 열린 결정 ②).
> `golden/*/원본.hwpx` 는 **소음·진동 섹션만** 담고 있어 목차를 담고 있지 않다. 파트 번호·이름을 확정하려면 **완본 보고서 1건**을 NAS에서 확보해야 한다. 그 전까지 `docs/naming.md` 의 파트 목록은 **초안**이며, 확정되지 않은 파트 번호를 **추측해서 쓰지 말 것**(`common.md` 환각 금지).

### 인풋 — 전 파트 공유

```
cases/small-env/{사업}/input/
  ├ 사업개요.txt              사업명·위치·규모
  └ 환경질측정_보고서.txt      측정값·용도지역·측정지점
```
파트가 늘어도 인풋은 사업당 이 한 벌이다. 그래서 `input/` 이 `{파트}/` 바깥에 있다.

### ★ 같은 보고서의 다른 파트도 인풋 자산이다 (2026-08-05 천안 실증)

한 사업의 보고서는 여러 파트가 **같은 데이터를 공유**한다 — PP 표(지점명·방향·이격거리·XTM/YTM,
천안에서 소음진동↔대기질 완전 동일 확인), 일 작업량, 투입장비, 사업명. 어떤 파트를 생성하든
**다른 파트 텍스트(0200 지역개황·0722 대기질·0727 소음진동 등)가 확보돼 있으면 삽도 판독보다 우선**한다.
정답지 참조가 아니다 — 생성하는 파트의 골든셋만 금지 대상이다.
파트별 구체 우선순위는 각 파트 rule에 (예: `noise-vib.md` §2-4).
인풋 수집 때 해당 파트 파일만 가져오지 말고 **자매 파트 파일도 함께 확보할 것.**

## 2. 파트 내부 3단 구조 (5/5 동일)

모든 파트가 같은 대분류를 쓴다. **순서·표기를 그대로 지킨다.**

| 대분류 | 표기 | 내용 |
|---|---|---|
| 가 | `가. 현 황` | 조사내용 → 발생원 현황 → 측정지점·일시·결과 → 법령 기준표 |
| 나 | `나. 사업시행으로 인한 영향예측` | 예측내용 → 예측지점 → 예측방법 → 예측결과 |
| 다 | `다. 저감방안` | 환경보전목표 설정 → 공사시 저감방안 |

> `가. 현 황` 은 **가운데 공백이 들어간다**(`현 황`). 5/5 동일하므로 오타가 아니다.

하위 번호 체계는 `(1)` → `(가)` → `1)` 순으로 내려간다.

## 3. 문체

| 규칙 | 근거 |
|---|---|
| 평서 종결 `~하였다` / `~조사되었다` / `~계획이다` / `~예측되었다` | 5건 합계: 하였다 33 · 계획이다 25 · 조사되었다 24 · 실시하였다 9 · 예상된다 8 · 예측되었다 7 · 나타났다 7 |
| **현황·측정 = 과거형** (`조사되었다`, `실시하였다`) | 이미 한 일 |
| **저감방안 = 의지형** (`~할 계획이다`) | 앞으로 할 일 |
| **예측 = 추정형** (`~예측되었다`, `~예상된다`) | |
| 1인칭·추측·완곡 표현 금지 (`~인 것 같다`, `~로 보인다`) | 관측 0건 |

기준 **초과**를 가리킬 때 보고서가 쓰는 낱말은 **`상회`** 다 (`초과` 아님). 예측결과 표의 판정 셀은 `만족` / `상회` 두 가지뿐이다.

> ⚠️ 검증 스크립트가 `초과` 로 검색하면 **상회 건을 전부 놓친다.** 실제로 이 규칙을 쓰기 전 집계에서 5건 모두 "초과 0건"으로 잘못 나왔다.

## 4. 표기 — 치환 스크립트가 깨지는 지점 ⚠️

### 가운뎃점이 3종류다

같은 문서 안에서 **세 개의 서로 다른 유니코드 문자**가 쓰인다. 눈으로는 구별되지 않는다.

| 문자 | 유니코드 | 빈도 | 나타나는 자리 |
|:--:|---|--:|---|
| `·` | U+00B7 (MIDDLE DOT) | 144 | 본문 산문 `소음·진동 현황`, 삽도 `소음·진동 영향예측지점도` |
| `ㆍ` | U+318D (ARAE-A) | 89 | 소제목 `(1) 소음ㆍ진동 발생원 현황`, 법령 인용 |
| `․` | U+2024 (ONE DOT LEADER) | 81 | 제목 `7.2.7 소음․진동`, 장 제목, 삽도 `소음․진동 측정지점도` |

**자리별로 고정돼 있다** — 5건 전부 같은 위치에 같은 문자를 쓴다. 즉 무작위가 아니라 원본 서식이 그렇다.

**규칙**:
1. 검색·치환 문자열은 **골든셋에서 복사**해 쓴다. 손으로 타이핑하면 `·` 로 입력되어 매칭에 실패한다.
2. 문자를 **정규화하지 않는다.** 통일하면 정답과 달라진다.
3. 검색어를 짤 때 가운뎃점을 **피해서** 잡는 편이 안전하다 (예: `측정지점도` 만으로 검색).

### 그 밖

| 항목 | 규칙 |
|---|---|
| 따옴표 | 소음환경기준 지역은 `“다” 지역` (곧은따옴표 아님), 목표기준 문장은 `‘가’ 지역` |
| 표 캡션 | 본문 참조는 `<표 7.2.7-1>`, 표 위 캡션은 번호 없이 이름만 (`현황조사내용`) |
| 삽도 캡션 | `소음․진동 측정지점도` · `소음·진동 영향예측지점도` — **가운뎃점이 서로 다르다** |
| 출처 표기 | 표·삽도 아래 `자) ` 로 시작. 법령은 `[별표8] <개정 2019.12.31>` 형식까지 그대로 |
| 주석 | `주) ` 로 시작 |

## 5. 머리글 / 바닥글

전 파트 공통. 사업명만 바뀐다.

```
머리글 : {사업명}
바닥글 : 제7장 환경 현황, 환경에 미치는 영향의 조사․예측․평가 및 환경보전방안
```
사업명 형식: `{시군} {읍면} {리} {지번}번지 일원 {사업종류} 조성사업`
예) `괴산군 청안면 금신리 153번지 일원 태양광발전시설 조성사업`

> 사업명은 본문·표 안·머리글·바닥글 **여러 곳에 등장**한다. 표 **안쪽** 텍스트가 치환에서 누락된 전례가 있다 (`noise-vib.md` 오류 레지스트리 Major).

---

## 6. 법령 인용표 — 손대지 않는다

각 파트에는 법령 기준표가 통째로 들어간다(소음진동편은 4종). **레퍼런스에서 그대로 가져오고 내용을 편집하지 않는다.**

바뀌는 것은 **어느 칸에 볼드·음영이 걸리는가**뿐이며, 이는 사업의 용도지역에 따라 달라진다. 자동 처리 대상이 아니라 **실무자 확인 항목**이다.

법령 개정 시에는 파트 rule이 아니라 **골든셋을 다시 받아** 반영한다 — 인용 오류는 보고서 반려 사유다.
